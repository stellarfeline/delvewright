# ADR-0037: Peak memory is bounded in map size — every whole-map stage runs over a chunked world store with a fixed working set

- **Status**: Proposed
- **Date**: 2026-11-01
- **Source**: the requirement that a larger map need no more memory and that every whole-map stage process the map in bounded chunks; the memory profile of `delvec build` and `delvec detail --all` over the town campaign (95 places, site region 588 × 176 × 830) and the gallery, taken with two instruments that share no configuration — heaptrack (allocation sites, Linux) and the process's own resident set read from `/proc` once a second beside its timestamped stderr (`tools/maintenance/rss-sample.sh`, committed with the round that landed §5 item 1's rest; the rows before it were taken with the same script before it was committed, as their commit bodies say), with GNU `/usr/bin/time -v` (Ubuntu's `time` package) and macOS `/usr/bin/time -l` as the whole-run figures; the engine tree at the revision this record lands with; CLAUDE.md "Host hardware never caps a capability", "Debug doctrine", "A craft question … is researched"; ADR-0006; spec-0113 §4.7 and §7; the sources cited in §4.
- **Supersedes**: nothing. Refines spec-0113 §7 (cost and caching of the reach graph) by naming the structures it keeps and bounding them.

## Context

The stages, in pass order, and what each holds whole:

1. **Assembly** (`assembled::assemble`): every placed non-air cell in one `BTreeMap<[i32; 3], BlockState>` — 18.4 M entries for the town, the 9.6 M beyond the judged columns included. The gravity settle walks it by column. The edit replay copies it (`Arc::make_mut`) once a script exists.
2. **The judged copy** (`Assembled::judged_within`): a second map of the 8.8 M cells inside the judged columns plus the barrier wall on its faces.
3. **Occupancy → the nav world** (`assembled::Occupancy`, `nav::World::from_occupancy`): one `BTreeSet` per cell class over the whole judged world, then `CellSet`s (a bitset over the bounding box where the class fills a 64th of it, a `BTreeSet` otherwise) and a `CellMap<Material>` that stays a `BTreeMap` over every non-air cell.
4. **Light** (`compiler::light`): one byte of passability and one of light per cell of the assembled box plus one layer, twice (sky and block): 2 × 2 × 86 M for the town; re-flooded per fixture the relight loop places. The region survey (`DW0210`) reads the reach closure.
5. **The reach graph** (`nav::world::reach`): a dense snapshot of the window — the built volume grown by 8 horizontally and 6 above — at 4 bytes of code and 2 of raw membership per cell (the town's window is about 93 M cells), the envelope index per column, and then, kept for the life of the process in `static` memos: every graph's node table (`nodes`, `flown`: one `Arc<NodeEdges>` per expanded node), the node bank (per flown node, every window cell its expansion read, at 8 bytes each, plus 32 run summaries that repeat its edges), and every closure taken (`Reach`: three `BTreeMap`s over the states, with each edge once in `succ` and once more in `preds`). A closure is cloned whole on every return, and a consumer that reads `preds` clones it again.
6. **The proofs over the closure** (`nav::leave`, `nav::horizon`, `nav::seat`, `nav::lethal`, `blind`, `sculk`, `light`): each takes its own `Reach`.
7. **The write judge** (`attached::judge_writes`, `resting::judge`): the load's 220,810 writes replayed in order over a world of their own, 16,959,995 changed cells judged with their neighbours; the outline table read over 9,072,903 cells.
8. **Emission**: text; small. The review world (`view::world`) builds every chunk's NBT payload in one map before writing region files.
9. **`detail --all`**: the 95 programs expanded and held (`Prepared`: the piece's NBT and tiles) until the whole is judged and written, then the battery, which is stages 1–8 again.

What grows with what:

- With **region volume** (the site plan's `region`, which the horizon's ground and sea fill whether or not a place stands there): the assembled map (18.4 M → 19.1 M placed cells when the region grows by 100 on every side), the review world's ground cells (58.2 M → 99.3 M) and its light arrays over the written chunks (2,014 → 3,300), the write judge. Measured, that growth is 1.86 GiB of peak for 57 M more region cells, all of it at the review-world stage. The reach graph does **not** grow with it: its window is the judged world's (the boundary's playable columns grown by 16, 270 × 512 columns for the town), and the widened town has the same 1,366,129 states and 8,882,406 edges.
- With the **playable region** under an `ocean` horizon: the rest states themselves — 1,201,111 of the town's 1,366,129 states are submerged sea cells inside the judged columns, carrying 7,016,576 of its 8,882,406 edges — and with them every structure of the reach graph.
- With **reached cells**: the node tables, the bank, every closure and every clone of one.
- With **configurations**: only the differing snapshot chunks (already shared in 4,096-cell chunks, spec-0113 §7) and one set of closures per configuration — the gallery's 23 configurations cost 1.34 GB in all; the town's one configuration costs ten times that.

### What the ruling asks

Peak memory is about constant in map size: a fixed working set, with every whole-map stage reading and writing the map in bounded chunks. Only a summary that crosses chunk borders may grow with the map, and the engine states its size before the build starts. No check gets weaker to fit: the reach closure, the leak floods, the light per region and the write judge keep their exact answers (CLAUDE.md "Debug doctrine"). Output stays byte-identical to the unchunked engine (ADR-0006). The hosting side meets the stated cost; the engine never refuses a map for its size (CLAUDE.md "Host hardware never caps a capability").

### Established practice

- **A chunked world store is the game's own representation.** Minecraft keeps blocks in 16 × 16 × 16 sections, each a palette and a packed index array, inside 16 × 16-column chunks inside 32 × 32-chunk region files, and loads and lights them one chunk at a time (the Anvil format the pinned server writes; the engine's own review world already emits it, `view::world`). Cited.
- **Light is flooded per chunk and spilled across borders.** The game's light engine and its re-implementations light one chunk's sections, then propagate across shared borders; the community specification of the algorithm (dktapps, *lighting-algorithm-spec*) does it in passes — sources per chunk, a flood that "must not influence any other chunks except the source chunk", then propagation "across their shared borders" over square groups of four chunks, after which a chunk that has sat in all four positions "is then fully light-populated"; replacing a chunk invalidates it and "the surrounding 8 chunks". Starlight (PaperMC) ties light sections to the chunk objects and holds "no separate state of its own", which is what lets it run per chunk in parallel. Cited.
- **Hierarchical path-finding over a portal graph.** HPA* (Botea, Müller and Schaeffer, "Near Optimal Hierarchical Path-Finding", *Journal of Game Development* 1, 2004, 7–28) "partitions the map into clusters and precomputes optimal local paths between entrance points of adjacent clusters", then plans "an abstract path through the cluster graph" and refines it inside each cluster. The reach graph's closure is reachability, not shortest path, so the abstraction is exact here rather than near-optimal: a state in one cluster reaches a state in another exactly when a chain of intra-cluster closures and inter-cluster edges joins them. Cited.
- **Breadth-first search over a graph that does not fit.** External-memory BFS (Munagala and Ranade, SODA 1999; Mehlhorn and Meyer, "External-Memory Breadth-First Search with Sublinear I/O", ESA 2002) keeps the frontier and one level's adjacency in memory and reads the graph by blocks; Mehlhorn and Meyer group nodes into clusters stored contiguously so that a block read serves many frontier nodes at once. The chunk is that cluster here. Cited.
- **Connected components over a volume too large to hold.** Isenburg and Shewchuk ("Streaming Connected Component Computation for Trillion Voxel Images", SoCG 2009 workshop) label a 10,000³ grid "using no more than 350 MB of main memory" with a streaming union-find that keeps only the components still active at the sweep front; Andres, Koethe, Kroeger and Hamprecht (arXiv:1009.6215, 2010) label "in a block-wise fashion" and reconcile labels across block faces by union-find. The engine's floods — the sea's seepage into the built volume, a piece's exposure, the party's air — are connected components of this kind. Cited.
- **Sparse volume libraries page leaf tiles in and out.** OpenVDB served voxel leaves through delayed loading for a decade before retiring it in 13.2.0 in favour of codecs; the lesson taken is to make the paged unit the storage unit (a section) and to keep paging out of the data structure's own API. Cited; the design choice drawn from it is authored.

## Decision

### 1. One world store, chunked, with a resident budget

The assembled world is held in **one section store**: 16 × 16 × 16-cell sections, each a palette of `BlockState`s and a packed index array, addressed by section coordinate; a section nothing wrote is absent and reads as what the level generator lays there (`plan::ocean_layer_at` under an ocean, air otherwise — the `Reached` distinction `Assembled` already keeps, now a property of the store). The `BTreeMap<[i32; 3], BlockState>` world and every whole-world `BTreeSet`/`BTreeMap` of cells derived from it (stages 1–3 above) are retired; the nav codes, the light bytes and the cell classes are **computed per section from the store** when a section is loaded, by the same per-cell functions that compute them today, and cached per section.

**One resident budget, in bytes, holds every structure that pages** — the section store, the reach graph's edge lists and node tables, the snapshot's pages, and whatever pages next (`reach/budget.rs`). Each states the **working set its walk needs**, measured from what it has had to hold and never set by a host: the lists' is the 3 × 3 ring of reach chunks as large as the largest any list has decoded, with the ring's buffered pushes; the snapshot's is four 3 × 3 rings of the tallest window's pages; the store's starts at a 3 × 3 × 3 ring of sections at the wide index and is **measured as the build runs**: an array read back within one turnover of the arrays the need holds — fewer arrays, over every store, come resident (made or read back) since it was given up than the need holds, and given up under the need now stated — was given up while the walk was still using it, and each time the stores are brought under the budget, a sample of read-backs of which half or more were such re-references doubles the need, until the walk's working set stays; an array given up long before is read back cold however few cells of it the walk touches, so a sliver written at assembly into a section placed long before, a second sequential pass over a spilled world, and a store another stage's growth pushed out, raise nothing. (Built first as a count of reads per array read back — fewer than 256 said thrashing — which doubled the need five times over the town's assembly, where a template writes a sliver of a few cells into each section a neighbour placed before it, and once more when a copied store was dropped and its reads left the sum: the rows up to item 3's tail below were measured under that rule, and its successor is measured in §5 item 5's rows.) The budget is the sum of the needs stated: the lists' and the snapshot's are independent of the map; the store's is the ring once every whole-map reader is sectional (§2), and the working set of a reader that walks cells at random while one remains (the leak floods, §5 item 5) — stated at the end of the run, never set by a host. Every structure counts the bytes it holds against one process-wide total; past the budget, the structure that just grew gives up its least recently used holdings first — down to three quarters of its own stated need and no further (`budget::spare`) — then every other is asked, the stores never below three quarters of theirs, until the total stands at three quarters of the budget: no structure is emptied for another's growth, which, measured on the town, had the stores give up every array each time the reach graph's lists and snapshot filled to their needs, and a walk within the stores' need read them straight back (the §5 item 5 rows). A holding given up is written to a scratch file in the system's temporary directory (never the output tree, which is the deliverable the determinism gates hash; a `--perturb` build has none) and read back on demand. A scratch file that cannot be opened is no file, and the structure holds its records in memory; one that was opened and then refuses a write or a read back stops the run with a message naming the file, the operation, the error and the bytes written — one policy for every spill (`reach/spill.rs`). **Neither the budget nor the section size is an input to any emitted byte** — proven in §4.

The judged world is a **column mask** over the store (the boundary's playable columns grown by 16, with the barrier wall as a rule of the mask's faces), not a copy. **Built otherwise, declared**: the judged world is a second store of the judged columns and the wall (`Assembled::judged_within`), which at the store's cost is 15.6 MiB on the town against 29.1 MiB for the whole; the mask would have every reader of the judged world consult the columns and the wall rule and saves that copy, and it stays owed. Restated once the store pages (§5 item 3's tail): the copy's arrays are paged under the one budget like the whole's, so what the mask would save in memory is the copy's palettes and section index (3,900 sections on the town) and on disk its 16,360,704 bytes of records, against a masked view type that every reader of the judged world — `get`, `in_box`, the write judge, the review world — would take, interleaving the wall rule's cells in cell order; on that balance it stays owed. `Reached` stays as it was: one word per column, a property of the columns and not of the cells. **A copy of a store shares every index array with the original until one of the two writes it**: the picture a review world starts from, a configuration's bytes and the load world the write judge reads are whole-world copies with sparse writes, and each costs its palettes, its section index and the sections its own writes touch; an array shared this way keeps the original store's clock until it is written (§5 item 5's second half, measured below).

### 2. Every whole-map stage reads the store by chunk

For each stage: how the map is chunked, what crosses a chunk border, and what may grow with the map.

| Stage | Chunking | Crosses a border | Grows with the map (stated) |
|---|---|---|---|
| **Assembly** | A template or a fill is clipped to the sections it covers and written section by section, in plan order. Gravity settles per column, inside one section column (every y-section of one (x, z) chunk), in the order the columns are met. | Nothing: a write is per cell, a settle per column. | Nothing. The store's scratch file is the map's size on disk, never in memory. |
| **Edit replay** | A batch's writes are applied to the sections they touch; the per-batch invariant re-proofs are the chunked proofs below over the sections the batch touched and their 1-section halo. | The halo. | Nothing beyond the proofs' own summaries. |
| **Cell classes and the nav world** | Per section, from the store, on load. The `World` keeps its premises (killing volumes, furniture, gates, seats) as the small declared lists it keeps today, and asks the store for a cell's class. | Nothing. | The premises: the campaign's declared objects, not its cells. |
| **Light** | The sky term is one top-down sweep per column (column-local). The block term is a flood per section over the section's own emitters and the light arriving at its six faces; a section whose face values changed re-enters its neighbours' queue; the flood runs to the fixpoint. Then every section is flooded once more with the fixed face values. The field is the pointwise maximum over every seed of `seed − distance`, so the fixpoint is the whole-world field whatever the section order (the same fact `compiler::light` already rests its determinism on). The relight loop's one ordered decision — the darkest deficient cell, ties by `(y, z, x)` — is a sort over the gathered deficient set, which is a list of dark cells, not a field. | The six face planes of a section: 6 × 256 light values, the light spill. | The deficient set: one entry per dark reachable cell, bounded by the dark count the diagnostic reports, never by the map. The per-region verdict (`DW0210`) is exact: it reads the fixpoint. |
| **The reach graph** | Partition the window into **reach chunks**: full-height columns S × S cells in (x, z), S a multiple of 16 and at least `WINDOW_MARGIN` (8), so that every launch out of a node, every cell `rest_kind` asks about where it lands, and every fall column lies inside the node's chunk or its eight neighbours. Expansion runs chunk by chunk with the 3 × 3 ring of snapshot sections resident; a node's edges whose target lies in another chunk are **portal edges**, written to the target chunk's inbound list. The envelope index (`Columns`) is per chunk. The closure from the roots is an external-memory BFS over chunks: a frontier per chunk; load a chunk, expand the nodes the frontier reached (lazily, as `body_reach_at` does today — a node flies only the launches that can reach an unreached rest cell), take its internal closure, push each crossing onto the neighbour's frontier, release the chunk; stop when every frontier is empty. The reached set is **one bit per window cell**; the edge lists live in the chunk's file and are read back when a proof asks for a node's successors or predecessors. | The portal edges at chunk faces; the frontier. | The reached bitmap: window cells / 8 bytes (11.6 MB for the town). The portal edges: one record per edge that crosses a chunk face, bounded by the states on chunk faces times the launch set — stated per build as "N portal edge(s) over F face cell(s)". The bank, the node tables and the closures of a chunk live with the chunk; a build that persists the bank (`DELVEC_REACH_CACHE`) persists it per chunk. |
| **The sea** | A submerged cell whose six neighbours lie inside the window and are water, with no collision top in the 3 × 3 × 2 neighbourhood that would give it a climb-out, has exactly the six dive edges and nothing else (`reach::expand`). Such **plain-sea** cells are not stored as nodes: when the closure reaches one, its whole connected component is flooded into the reached bitmap (a second bit per window cell marks it plain), the non-plain water cells on its boundary join the frontier, and nothing is listed, tabled or counted as a portal; a plain cell's six dives are computed when a reader asks for its successors or for a neighbour's predecessors. A body that reaches any cell of the component reaches every cell of it, and leaves it only through its boundary. This is exact for every consumer because every edge out of a plain-sea cell is a dive to a plain-sea or boundary cell, and the closure of the component is the component (built as *The plain sea, measured* below says). | The component's boundary cells. | Nothing beyond the bitmap: the summary is the bitmap itself. The binding line keeps counting every state and every dive, summarised or not, so `DW0921` and the reach binding read the same numbers. |
| **The leak floods** (`DW0851` sea seepage, piece exposure, party air, `DW0318`) | Block-wise connected components: label per section, record the labels on each face, union across faces, relabel on the second pass (Andres et al.; Isenburg and Shewchuk). | The face labels. | The union-find over face labels: one entry per distinct label on a section face, stated as "L face label(s)". |
| **The write judge** (`DW1002`, `DW1076`) | Replay the load's writes in order over a copy-on-write view of the store: a write touches the sections it covers and their 1-cell halo; a changed cell is judged with its neighbours as it lands; a section no later write touches is released. The runtime arm judges each configuration's writes the same way. The outline check is per cell with a 1-cell halo. | The halo. | Nothing: each write's working set is its own sections. |
| **Emission** | Already streamed: a function is written when complete. | — | — |
| **The review world** (`view::world`) | Region file by region file (32 × 32 chunks): build one region's chunk payloads, write, release. The light it carries comes from the light stage's store, not a second flood. | Nothing. | No more than one region file's payloads at a time. |
| **`detail --all`** | Each place's program is expanded, judged against the whole and written in place order as today; the pieces held until the one judgement are the campaign's own `.nbt` bytes, whose size is stated with the run. The battery is the chunked build. | — | The prepared pieces: the sum of the pieces' bytes, a property of the campaign, stated. |

### 3. The engine states a build's cost before it starts

Before stage 1, `delvec build` and `delvec detail` print one line, `resource cost:`, **computed** from the documents and the store alone — the site plan's region, the horizon, the configurations the quest plan enumerates, and the budget of §1 — stating the working set (the budget, by the needs that sum to it), each summary's bound (reached bitmap: window cells / 8; portal edges and face labels: an upper bound from the window's chunk-face area and the launch set; the plain-sea summaries: at most one per water body of the horizon), and the scratch files' size (placed sections × section bytes; the reach graph's records). **The rest census** (`cost::RestCensus`) is how the store enters the bounds: the window is read section by section through the one block classification (`blockshape::collision_class`), and per column the cells a body can rest in at most are counted — one standing candidate over every surface (a block a body stands on with no such block over it), every climbable cell, every fluid cell and every cell of the horizon's sea band — an upper bound on a closure's states by construction (a surface under a torch or a ledge a body cannot fit on counts a rest cell no body takes; nothing a body rests in goes uncounted). A node's edges are at most the launch set's landings with the cell moves, and no more than the rest candidates within `LAUNCH_REACH` (5) columns of it, where every launch lands (a sprint jump carries 3.63 cells, a fall drifts under 4.5); a water node has at most its six dives. Summed over a reach chunk, that bounds what its lists decode to; summed over the nodes within reach of a chunk face, a water cell on the face line crossing it at most once, it bounds the portal edges of one closure. The line takes the tighter of the census's bound and the plain one (every cell a node with every edge) for both figures, and prints the census beside them. Each figure's measured counterpart is printed as the run ends (`reach portals:` the most portal edges in one closure, `reach graphs:` the graphs memoised, `reach lists:` the largest decoded chunk, the exposure line's section component labels, `world store pages:` the need and the scratch file), and the factor of each bound over its measure is stated per figure in the measured rows below. The line is part of the build's binding output and is written into `validation/resource-cost.json`, which holds the computed cost and nothing measured, so it is byte-identical across builds (ADR-0006). A measured peak never enters the output tree: it is the second instrument that cross-checks the computed figure, taken with GNU `time -v` and the `/proc` sampler, and goes in the commit bodies and this record. The hosting side meets the stated cost (CLAUDE.md "Host hardware never caps a capability"); the engine does not refuse a map for it.

### 4. Determinism, and how it is proven

What the tree proves, test by test, and what it owes:

- **No answer of the reach graph depends on its chunk side or the resident budget** (`reach/agreement.rs`, `no_answer_depends_on_the_chunk_side_or_the_budget`): fifteen worlds asked of a closure kept in chunks of sixteen columns, of seven, and of two under a budget of one byte, and of one over a snapshot paged to nothing — every state, every state's successors and predecessors in order, the flags, the counts and both node tables equal; and in every reading the records read back from the lists are the edges counted at join. The closure is the one every launch gives (`the_chunked_closure_is_the_one_every_launch_gives`); each reader by chunk is held to its plain form over the same closure (`a_walk_by_chunk_answers_what_a_plain_walk_answers`, `the_route_tree_by_chunk_is_the_one_search_gives`, `the_portal_edges_are_the_edges_that_cross_a_chunk_face`); each store is held to a map (`a_list_kept_by_chunk_answers_what_a_map_answers`, taking the rewrite branch and a copy mid-stream under a budget of one byte; `a_table_keyed_by_chunk_answers_what_a_map_answers`; `the_states_answer_what_a_map_of_them_answers`); records read back while writers append are the records written (`spill::tests`, run on the Windows target in CI); the bank's spill holds only the records its slots name, the bound judged before the write (`bank::tests::a_variant_past_the_bound_is_never_written_to_the_spill`), so two runs that keep the same variants report one spill size — a record written past the bound and dropped had made `reach_cache`'s check-against-the-bank comparison red once in three gate runs.
- **The section store answers what a map answers** (`sections::tests::a_section_store_answers_what_a_map_answers`): 60,000 generated inserts and removes over three cell pools (one section; sections across the origin; a sparse spread of 400 × 100 × 400), 300 distinct values so dense sections outgrow the one-byte index, a copy taken mid-stream, and after every 5,000 edits the whole iteration and 20 boxes read back in order against a `BTreeMap`; the whole iterated, the keys, the values, the section count, the copy's independence, `retain`, and the store emptied to zero sections and zero bytes. Perturbations, each restored from a copy: the local index y-leading, the box clipping z one short, and the ly advance keeping its section each red it; no palette compaction reds `a_palette_forgets_the_values_no_cell_holds`. The town's output tree is byte-identical to the engine before the store (below), which is the test on the one map that matters.
- **The review world's light by strip is the whole-box flood** (`view/world.rs`, `a_strip_of_light_is_lit_as_the_whole_box_lights_it`): generated boxes, cell for cell, across straddling strips, with the halo one below the exact one shown to fail.

### 5. Implementation order

By memory saved per unit of work, from the profile:

1. **The reach graph's process-wide memos** — the bank (2.5 GB), the node tables (1.1 GB), the closures and their clones (1.9 GB), the flight memo (0.6 GB), the snapshot (0.6 GB): about 7.5 GB of the town's heap, held to exit. First the bank, spilled to the scratch file (one slot per variant in memory): landed with this record and measured below. Then the closures: `body_reach_at` returns the memo's shared `Arc<Reach>` instead of a clone, a reader that grows a closure copies it only when it has a launch to fly (`Arc::make_mut`), the leave proof reads `preds` in place instead of cloning it, and a kept closure holds its edge lists at their length: landed and measured below. Then the closures' edge lists and the node tables kept by reach chunk in a scratch file under a resident budget, and the closure taken as the breadth-first search over reach chunks of §2, with the proofs that walk a closure reading it by chunk and the budget the working set a walk by chunk needs: landed and measured below. Then the rest of the item, landed and measured below: the window snapshot paged (hash-consed 4,096-cell pages in a scratch file, a resident budget of four 3 × 3 rings of the tallest window), the node tables keyed by chunk with packed slots, the bank persisted chunk by chunk, the reached states held as the bitmap and the kinds by block, and the portal-edge line. The flight memo is already bounded by a constant (`MEMO_ENTRIES`) and leaves this list.
2. **The review world** (the build's peak increment, about 3.3 GiB over the plateau): the ground cells walked rather than gathered (landed with this record), then the light flooded strip by strip of chunk columns with the exact halo of its reach, and the copies of the configuration's block map and of its files dropped: landed and measured below. What remains of the review increment is the configuration's own block map beside the picture it was taken from, which the section store of item 3 retires.
3. **The assembled world and its judged copy** (1.4 GB, and the write judge's own map): the section store of §1, with the judged world as a mask. The store landed and measured below (`compiler::sections`), the judged world as a second store, declared in §1; the write judge's map, the review world's block map and every whole-world `CellMap` take the store with it. The tail, landed and measured below: the store's index arrays paged under the one budget with the need measured from the walks (§1); the occupancy's cell sets built in the dense form directly, so the stage-3 transient of §4 is retired; and the shipped templates re-encoded as placed in waves of at most `TEMPLATE_DECODE_BYTES` (16 MiB) of decompressed template at once (`par::map_within`), which was the kernel's maximum over the plateau.
4. **Light**: per-section flooding over the store; the arrays are a smaller holder today (a few hundred MB) and fall with the store. Landed and measured below: the field held by section, one byte where a section reads alike, flooded section by section to the fixpoint.
5. **The sea summaries and the leak floods**: the plain-sea components, which take 1.2 M of the town's 1.37 M states out of the graph, and the block-wise floods. Landed and measured below: the party-air flood by section; the need judged by re-reference distance, with the stores given up by least recent use and a copy's shared records cold; a template written and the judged copy taken section by section; a structure brought under the budget giving up its own excess and no more; and the cost line of §3. 6. **`detail --all`'s prepared pieces**: stated, not chunked; they are the campaign's own size. Landed: `detail prepared: N place(s) held until the one judgement, B byte(s) of structure template over F file(s) …`, printed by check and commit before the judgement.

## The closure by chunk, measured

The closure is taken as the breadth-first search over reach chunks of §2 (`World::close`, `World::fly_chunks`): the cell relation is closed with a frontier per chunk, each crossing pushed onto the frontier of the chunk it lands in; the launches are flown in rounds, every standing or holding state whose envelope still holds an unreached cell flying toward it, each judged against the closure as the round found it, grouped by chunk and joined while that chunk's lists are the ones read. The snapshot is still the window-wide one, so loading a chunk's 3 × 3 ring is loading nothing; the chunk is the unit of list traffic and of the visit count. The proofs whose answer is a set read a closure by chunk (`Reach::reaching`, `Reach::preds_by_chunk`, the learned route tree as a per-chunk least-cost search and one predecessor sweep, the blinding flood's layers); `DW0921`'s way in and the mob reach's breadth-first path keep their own order, which is their answer. The lists' resident budget is the working set a walk by chunk needs: 9 × the largest decoded chunk plus 9 × 2 × 64 KiB of buffered pushes (46.6 MiB on the town, its largest decoded chunk 5,295,392 bytes).

**The one change §4 allows, declared.** Before, a round's nodes were flown in batches of 2,048 in cell order, each batch re-judged against what the batches before it had grown, so which launches were flown — and with them the edges joined, the launches simulated and the arcs credited — depended on that global order. ## The light field by section, measured

`LightField` (`compiler::light`) keeps its two bytes per cell — passability, sky and emission in one, light in the other — in 16 × 16 × 16 sections, each a single byte where every cell of it reads alike (the sky over open ground, the dark under it, the middle of a lit room) and 4,096 bytes otherwise. The sky term is one top-down sweep per column of sections, a cell over the box being open sky. The flood visits one section at a time over a dense scratch of it and the ring of its neighbours' cells, drains brightest-first as the whole-box flood did, stores what changed, and queues every neighbour whose face cells it brightened, to the fixpoint; a fixture that keeps its cell's passability seeds its section and lets the rise settle, one that changes it re-sweeps its column and floods again. The queue is a `BTreeSet`, so a run visits sections in one order; the field is the pointwise maximum over every seed of `seed − distance`, so the fixpoint is the one whole-box field whatever the order. ## Item 5's fourth part, measured: the write sequence by chunk

**The judge's working set was the load's row, and is now a chunk.** The previous section found the write-sequence judge's own stores never given up, and its working set one x-row of the load's sweep: the ground steps are emitted x-major, so one replay of the whole load in load order touches the sequence's world one x-row of sections at a time — O(z-extent), about 300 sections on the town — resident only because the budget had slack there. The exact bounded form that section named is built (`attached::replay_by_chunk`): the load is replayed once per chunk of 4 x 4 section columns some write reaches, over the chunk and a halo of 16 cells — every write in load order, clipped to those columns (a `fill` clipped as a box, never laid whole) — and only what lands in the chunk's own columns is kept: the cells changed, the blocks asked, the drops, the falls. **Why it is exact.** A cell's verdict reads only the cells its block's rules name, and a falling block's the cell below; so a cell's state can come to differ from the whole replay's only by a drop, a drop only through such a read of a cell that differs, and a cell whose block never reads anything never drops. The replay marks, per cell, the faces read by every state the cell ever held, follows the reads from every marked cell of the chunk through every marked cell, and if they reach a cell outside the halo that some write reaches, the chunk is replayed over twice the halo, until none does or the halo holds every write. A cell no write reaches holds what the generator put there, which depends on its height alone; under either horizon that is air, water, stone or bedrock, none of which reads a neighbour (a generator whose blocks did would replay the load whole, and the line says so). The drops are sorted back into the whole replay's order — function, line, then cell, the order a write's asks and a function's falls are taken in — and the cells the load leaves are kept chunk by chunk for the runtime arm, which reads them. ## The plain sea, measured

The plain sea is summarised in the reach graph (§2's sea row, §5 item 5's other half). A **plain-sea cell** is a submerged rest state each of whose six neighbours lies inside the window and holds a water rest state, with no collision top in the 3 × 3 × 2 cells round it and over it — the cells `reach::expand` gives exactly six dives and nothing else (no climb out, no open-sea flag, nothing flown). The repair is in the store, not in the figure: **the scratch file holds one region per array alive** (`sections::Region`). Every region is one size, the wide record's (8,192 bytes), so any free region serves any array; an array keeps its region across read-backs and give-ups — given up unchanged, its record stays and nothing is written; changed, the record is rewritten into its own region (`spill::Spill::write_at`, positional like the append); a region a copy shares is never rewritten while the copy holds it, since a record is read by every holder of its region — and a region whose last holder drops it serves the next array before the file grows. ## Consequences

- A build's resident memory is the budget plus the stated summaries; a map twice the size takes twice the disk under the scratch file and the same memory. The hosting side reads the `resource cost:` line.
- Every whole-world `BTreeMap<[i32; 3], _>` and `BTreeSet<[i32; 3]>` in the compiler becomes a per-section array or a declared list (`BlockMap` and every `CellMap` are the store; the occupancy's sets are built in their dense form from the first cell); a new pass that wants the whole world asks the store for it section by section, and a pass that collects cells into a whole-world set is the shape to refuse in review.
- The reach graph's edge lists leave process memory: a proof that walks `preds` or `succ` reads them from the chunk's file through the same `Reach` API; the API keeps its shape and its `Clone`, a copy sharing the spilled records and copying the buffered ones.
- The node bank is per chunk, persisted per chunk; a run that sets `DELVEC_REACH_CACHE` keeps the same hit rule (every read cell equal) at a chunk's granularity.
- `spec-0113` §7's baseline table gains the memory column and the chunk-size invariance criterion.
- Every scratch file is written in the system's temporary directory, unlinked as soon as it is open, and read and written positionally; its one failure after opening stops the run (§1). A build's disk is the map's size there, never under `-o`.
- One budget module is the only place a working set is summed or a holding given up; a new paged structure states a `Need` and registers, and adds no budget of its own. The section store is registered: the lists, the snapshot and every store in the process give up to one total, and the stores' scratch file follows the one spill policy.
- A transient whose size is pieces × threads — a decoded tree per worker — is taken in waves under a stated cap (`par::map_within`), never one per thread.
