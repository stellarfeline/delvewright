## 1. What a question is **[cited: CLAUDE.md]**

A question to the user asks for a creative judgement that needs a person's attention, in words a player with no engine knowledge can answer. The test is in the sentence: can a player who has never seen `delvec`, a DW code, a schema or a file path answer it from the message alone, and is the answer a judgement about the delve rather than about the toolchain. *Shall the town be seen at the end of the afternoon or at noon?* passes. *The DSL has no spelling for late afternoon — `noon`?* fails twice: it names the engine, and it asks the person to choose between an engine limit and a wish.

A refusal, a limit, a default or a workaround is never a question. The agent decides it by a stated default (§3), or the engine is changed so it cannot arise (§7), and in debug mode (§4) it is recorded. A departure the **player will see** — a forge of campfires where the design said lava, windows where it said an open shop front — is reported in the final report in player words whether debug is on or off; the engine limit behind it is reported only under debug.

## 4. Debug mode

### 4.1 The flag **[cited: Rust's `RUST_BACKTRACE`, twelve-factor config — §12.1; authored where stated]**

`DELVEWRIGHT_DEBUG` is an environment variable of the creator's shell, read at Init I0 beside the mode and written into the run's environment file by I4 (§7.5). Unset or `0` is **off**; any other value is **on**. It is never a plugin `userConfig` option, which a user sees in a settings screen: debug is for the engine developer, and a knob a user can see is a question a user is asked. **The released default is off**, and `SKILL.md`'s Init table says so in the I0 row. The flag changes no document, no emitted byte and no gate: it decides what the run's final report carries, and nothing else. [authored: the variable's name and the one-row placement]

### 4.2 What is recorded, and by what **[authored]**

Off: the agent takes every default of §3 silently, meets every refusal, limit and workaround silently, and the final report carries none of it. On: every one of these is **an event**, recorded the moment it happens by one tool, `scripts/debug-note.py`, which appends one row to `<campaign>/.out/technical.jsonl` (build output, never committed) and exits 0 — and when the flag is off, exits 0 having written nothing, so the page's instruction is the same either way and no step branches on the flag. A row carries `kind` (`default` | `refusal` | `limit` | `workaround` | `departure`), `step` (the page step, `init`, `1`…`13`, `9/<place>`), `what` (one sentence, for the engine developer), and for a `refusal` the `code` and `count`, taken from the `delvec` stderr the tool is handed by path (`--from <file>`), never retyped. A place author's return already names any capability it needed and the grammar lacks (spec-0121 §5); the orchestrating session records that sentence as a `limit` event with the place as its step.

### 4.3 The report **[authored]**

On, the final report of step 13 gains one section, **Technical decisions and engine limits**, written for the engine developer and rendered by `scripts/debug-report.py` from the rows: one subsection per kind in the order of §4.2; refusals as a table *code · count · where · what was said · repair*, the shape of the evidence runs' *Refusals, in order*; a closing line with the counts per kind and the total, computed from the rows. The same section is appended to `GENERATION.md` under the same heading, so the record outlives the chat. Off, neither tool writes a word and `GENERATION.md` carries what it carries today (the toolchain, the Detail table, the staging gate's result). A report whose section exists while the flag is off, or is absent while rows exist, is the renderer's defect, and `tools/tests/test_debug_report.py` reds on both.

## 5. The gate: a new ask outside the list reds **[authored]**

`tools/ci/check-skill-page.py` gains **rule 22**, with its binding count and denominator printed like every other rule. It reads `SKILL.md`'s ask table — the table whose header cells are `id`, `where`, `what the user is asked, in player words`, `what the run waits for` — and every page file, fences tracked, and holds three things:

1. **Every ask lies in a row.** A line of any page file that matches the ask pattern — `ask(s|ed|ing)? (the user|them)`, `wait(s|ing)? for (an answer|the user|a yes|an explicit yes)`, `STOP` as a whole token, `end your turn` — is inside a section whose heading the table names in its `where` cell (by the anchor the page's own contents list uses), or is a line of the table itself. A match anywhere else is a finding naming the file and line.
2. **Every row binds.** Each row's `where` section exists and carries at least one such line; a row nobody's page executes is the unrun shape.
3. **The offers are not stops.** A line matching the offer pattern — `offer(s|ed)?`, `may (choose|pick|stand)` — carries no match of the ask pattern within its paragraph.

The pattern is lexical and the rule says so in its own docstring: it proves that every stop the pages spell is one the table lists, never that a stop is a design question — that is §1's test, applied by a reader. The perturbation that reds it: add `Ask the user which provider the key is for` to `references/init.md` I7 under no listed heading. The perturbation that reds rule 2: delete A1 from the table while `references/workspace.md`'s language line stands.

## 6. Step 9 in parallel

### 6.1 The check and the commit are two runs of one verb **[cited: `crates/delvec/src/detail.rs`; authored]**

Today `delvec detail <campaign> <place>` prepares the place (binds the handing, expands at the frame, voids, gates, audits, probes light), judges the whole as the run would leave it (`judge_run`: the bindings check over the detail plan with this piece standing in for the library's copy), writes the piece and the plan row, and runs the battery (the whole built in memory through the build's own observers). One agent at a time follows: two checks at once race on `detail-plan.json` and the prefab directory, and judge a whole the other is changing (spec-0121 §7).

The verb gains **`--check`**: `delvec detail --check <campaign> <place>` runs `prepare` and `judge_run` against the whole **as committed on disk** — the detail plan and the library as they stand — and **writes nothing**: no piece, no row, no battery. Exit 0 says *this program would commit against the whole as it stands now*; any other exit is the verdict the commit would give, in the same words. `--check` with `--all` is refused (`--all` is the orchestrator's re-detail after a plan edit, which is a commit by nature). The place author's check becomes `detail --check`; the orchestrator's commit stays `detail <place>`, unchanged.

**One implementation**: `--check` is the commit's own `prepare` and `judge_run` with `write_one` and `battery` not called — the same functions, the same `Prepared`, the same diagnostics. No second judge exists to drift. The agreement test `crates/delvec/tests/detail_check_agrees.rs` runs both over the gallery's site-plan places and over each of three perturbations (an undersize piece, `DW0843`; an unanswered seam, `DW0844`; an owed name unbound, `DW0845`) and asserts the diagnostic lists equal, code for code, and that `--check` left the prefab directory and `detail-plan.json` byte-identical.

### 6.2 Concurrency, and where its bound comes from **[cited: `std::thread::available_parallelism`, cargo's `build.jobs` — §12.2; authored]**

Place authors run **concurrently**, up to a bound **N the engine states**: `delvec allocation --all` prints one more line, `concurrency: N = min(places to author P, max(1, cores C / 2))`, where C is `std::thread::available_parallelism()` read at that moment (it honours affinity masks and cgroup quotas and reads no load) and P is the number of places the plan allocates a box to that have no passing program. The divisor is the engine's own: an author's heaviest tool is a render to look, which on a CPU backend takes every core Lumenwright's pool is given, and a check holds one whole in memory; two cores per author is the floor at which a check and a render do not starve each other on the machines the evidence ran on, stated here as **authored** until a measured peak replaces it — every `--check` prints its own peak resident size (`getrusage`) on its binding line so the record carries the number to replace it with. The orchestrator never types N: the handout's header carries the line, and `scripts/handout.py` prints it on stderr with the rest of the binding.

### 6.3 The loop **[authored]**

1. The orchestrating session runs `handout.py` for each place of the first wave — the critical path from `entry` in order, then every other place in allocation order, scenery last, at most N — and launches each agent with the Agent tool on the printed line, as spec-0121 §4 says. The handout says which neighbours are detailed **as of the handout**, and tells the author that its check reads the whole as it stands when the check runs, so a neighbour may have landed since. Beside each handout `handout.py` writes the place's `allocation.json` and a copy of the **starter generator** (§8): the author's step 1 is to copy it to `design/generator/<stem>.py`, run it and see `detail --check` green before building anything, and the handout states that nothing outside its reading list — the engine's source, its gallery, another campaign — is needed or read. [authored: the evidence's place authors each spent the opening of their run researching how to write a generator]
2. Each author iterates with `grammar expand` and a render, and checks with `delvec --prefabs … detail --check <campaign> <place>`; it returns the report of spec-0121 §5 with the exit of its last check.
3. On each return, in return order, the orchestrator **commits**: `delvec --prefabs … detail <campaign> <place>` — serially, one commit at a time, never while another commit runs. Exit 0: the Detail row is recorded and the next unstarted place's handout is written and its agent launched, keeping at most N in flight. Any other exit — the author's check passed against a whole a neighbour has since moved, or passed and the battery over the committed whole refuses — is handed back as the next attempt's refusal: `handout.py` runs `detail --check` on the program the author left and embeds the verdict verbatim — or, where the battery over the committed whole refused (a refusal `--check` by design cannot see), embeds the commit's own captured output, handed to it as `--from <file>` and never retyped — and a fresh agent is launched on it. The three-of-one-code stopping rule stands per place.
4. A spine place refused three times with one code stops new launches (spec-0121 §5); authors already in flight return and are committed or handed back, and the cause is acted on before anything else is launched.

### 6.4 Writes that cannot be seen half done **[cited: POSIX `rename` — §12.4]**

A commit's three writes — the piece, its report and `detail-plan.json` — each go to a temporary file in the same directory and are moved into place with `rename`, which POSIX requires to be atomic: a check running at that instant reads the old file or the new one, never a torn one. An author's own files are its own: `programs/<place stem>.json` and `design/generator/<stem>.*`, distinct per place, never another's. The battery runs after the commit's writes and reads a committed whole.

### 6.5 What `GENERATION.md` records

The Detail table of spec-0121 §6, unchanged in columns; the exit recorded is the **commit's**. One line above the table states the wave bound as `allocation --all` printed it.

## 7. The engine defects the questions stood on

### 7.1 The clock in ticks **[cited: vanilla `/time set <ticks>`, `crates/dsl/src/world.rs`, spec-0081; authored where stated]**

Vanilla's clock is one number, `dayTime`, and `/time set` takes a keyword or a tick count; the tick form is the general one, and the engine's own doc comment on `WorldTime` says so. The DSL exposes it: `world.time` (and with it `set-time`, a design row's `time` and a camera's `sky.time`, which share the type) accepts a third spelling, **the clock statement** `{"daytime": <0..=23999>, "phase"?: <moon phase>}`. `daytime` is the vanilla `dayTime` modulo 24000; `phase` follows spec-0081's rule exactly — required where the moon is at or above the horizon at that tick, refused where it is below (`DW0931`), the day is the phase's index or the world's. Emission is the existing path: a clock statement is a `Clock` and `WorldTime::token` emits `day × 24000 + daytime`; no keyword campaign's bytes move. The sky-light model and `DW0496` already read the clock by tick. A `daytime` outside the range is the schema's refusal (`DW0100`), as every out-of-range number's is. Canonical form writes the object with its keys in alphabetical order, as `delvec fmt` holds every document. *Late afternoon* is `{"daytime": 10500}`, and the design gate shows the picture under it. [authored: the field name `daytime`, chosen to match the vanilla query and the binding line's own word]

### 7.2 A creator's test level is the creator's **[cited: CLAUDE.md, *a primitive encodes a mechanism, never a design decision about what it is for*; authored]**

`world.demo_level` is a mechanism — *this campaign ships no approved design record* — welded to a purpose — *because it is a row of the engine's `docs/demo-levels.md`*. A creator who wants a small level to test a cut with cannot have the mechanism without the engine's queue, and the staging gate refuses `DEMO-UNQUEUED` on a document in another repository the creator never edits. The two are separated:

- `world.json` `demo_level` is **replaced** by **`test_level`** (opt, bool). `true` declares a level built to try something, with no approved design record: the staging gate's design-record rows measure zero over it; a `design/cameras.json` row needs no `answers` row of a `design.json` the campaign does not carry — on a test level `answers` is omitted and the camera's `note` names what it frames, and `DW0721`'s *not a row of design.json* arm does not fire; `delvec cameras` draws the record without a `design.json`; nothing a player meets changes. A test level still passes the design gate (A2 is a design question: the person says yes to the walkthrough); what `test_level` removes is the record, not the yes.
- A test level that **also** carries `design.json` is refused at validate: **`<DW-new-1>`**, *`<campaign>` declares `test_level: true` and carries `design.json`; a level with an approved design is not a test level — drop one.* The code is asserted by a test and listed in `docs/reference/compiler.md`.
- `manifest.json` carries `test_level: true` where declared, as it carried `demo_level`; the staging gate refuses a source and a build that disagree, as it does today.
- The staging gate's `demo_refusal`, its `DEMO-UNQUEUED` verdict and its reading of `docs/demo-levels.md` are **removed**. Whether every built row of the engine's demo queue names a directory that exists is the engine repository's own concern: `tools/ci/check-demo-queue.py` (new, small) reads the queue and refuses a Status cell naming `campaigns/<id>` that the content pin's tree does not carry. The queue's rule text changes from *declares `demo_level: true`* to *declares `test_level: true`*.
- The gallery binds `test_level` by a probe (`gallery/probes/`): `test_level: true` beside `design.json`, refused `<DW-new-1>`; the primary, `test_level: true` with no record, builds.

### 7.3 A view stands where a body's eye stands **[cited: `crates/dsl/src/siteplan/mod.rs` `View`, `crates/delvec/src/compiler/view/camera.rs` `Camera`]**

`View.eye` and `View.look_at` are `[i64; 3]`; a showcase camera's `pos` is `[f64; 3]` and a body's eye stands 1.62 above its feet. Both become `[f64; 3]`. The view-distance proof (`DW0956`) measures the same distance over floats; the plan's view renders take the float pose. Canonical form writes floats as JSON numbers with the shortest round-trip spelling, which serde_json already does, so a whole-number view written `[54, 85, 101]` stays those bytes and determinism holds. The gallery's `views[]` gains one view at a half-block eye.

### 7.4 Light is judged where a place has been built **[cited: `docs/reference/interior-lighting.md` — light is placed while the room is designed, the engine only checks; authored]**

A stand-in is the derivation's placeholder for a place nobody has designed yet; its interior is dark because no one has placed its light, and judging it is judging a room that does not exist. `compiler::light`'s `DW0210` gate **excludes every cell inside a massed place's frame** — the places `validation/blockout.json` lists under `massed` — and its binding line states the exclusion: `DW0210 binding: N reachable cell(s) judged, D dark; E cell(s) under M stand-in(s) not judged`. A fully detailed build excludes zero and the line says `0 under 0`. The light probe `delvec detail` runs over each place's own piece is untouched — that is where a place's light is judged, by the author who placed it — and the whole's gate judges every detailed place and every cell the whole owns (streets, rings, commons). Step 8 therefore exits 0 over unlit stand-ins, and the battery, the exposure gate and the leave-proof report at step 8; `references/build.md` stops describing `DW0210` on stand-ins as a state to carry.

### 7.5 A session's state lives with the session **[cited: `references/init.md` I4 and I8, `references/build.md`; authored]**

`~/.delvewright/env.sh` is one file per machine, and `DELVEWRIGHT_PREFABS`, `DELVEWRIGHT_MODE`, `DELVEWRIGHT_ENGINE` and `DELVEWRIGHT_SKILL` in it are properties of a **working directory**; `validation/delve-output` is one tree per engine checkout. Two sessions on one machine rewrote each other's library and built into one tree. What is per machine stays in `~/.delvewright/`: the engine clone at the pin, `bin/`, the client jar — read-only after Init. What is per session moves to the working directory's own build output, `.out/` (gitignored in the content repository and in every campaign; `SKILL.md`'s I8 already creates it):

- **I4 writes `$PWD/.out/env.sh`**, every variable it writes today plus `DELVEWRIGHT_DEBUG` (§4.1), `DELVE_OUTPUT="$PWD/.out/delve"` and `DELVE_DOCKERFILE="$DELVEWRIGHT_ENGINE/validation/Dockerfile.delve"` — the pair `references/build.md` already names as what travels together. ## 12. Research record

Each item answers the one question asked and stops.

### 12.1 A debug switch is an environment variable read at start **[cited]**

Rust's standard library reads `RUST_BACKTRACE` (and `RUST_LIB_BACKTRACE` ahead of it): *if this is set to `0` then `Backtrace::capture` will never capture a backtrace; any other value set will enable it; if neither is set, capture is disabled* — a developer-facing switch whose off state is the released default and whose on state is any other value. The twelve-factor method stores config in environment variables because they are *fully orthogonal*, change between deploys without touching code, and have *little chance of being checked into the code repo accidentally*; what does not vary between deploys belongs in code. `DELVEWRIGHT_DEBUG` follows both: unset/`0` off, anything else on, read once at Init, never in a committed file.

### 12.2 A concurrency bound is derived from the machine's core count **[cited; the divisor authored]**

`std::thread::available_parallelism` returns *an estimate of the default amount of parallelism a program should use*, honours *a process-wide affinity mask or cgroup quotas* where it can read them, does not account for *current system load*, and is *recomputed every time this function is called*. Cargo's `build.jobs` defaults to *the number of logical CPUs*. Both derive a parallelism bound from the machine, read at run time, and neither from a constant. §6.2 reads the same function; the divisor 2 is this spec's and is marked so.

### 12.3 The game's default field of view is 70 **[cited]**

Minecraft Java Edition's video options give a default FOV of **70**, displayed as *Normal*; the slider runs 30 to 110. A camera row written from a hand-placed camera whose person said nothing about the slider takes 70.

### 12.4 A file replaced by `rename` is never seen torn **[cited]**

POSIX `rename`: when the new path exists it is removed and the old path renamed to it, and *a link named new shall remain visible to other threads throughout the renaming operation and refer either to the file referred to by new or old before the operation began*; the rationale *requires that the action of the function be atomic*. §6.4 writes each commit file beside its target and renames.

### 12.5 Whether an adventure-mode body opens a wooden door by hand **[open]**

Not established here: the vanilla page read states neither the adventure-mode rule nor the iron-door rule in a sentence this record can quote. §11 row 8 names the question and the instrument (the pinned jar, once) and nothing is built on an answer.
