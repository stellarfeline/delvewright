- **What it is for**: a corridor the party walks down and never reaches the end of, until the story lets it. Each time a body crosses a plane the engine moves it back by a fixed whole-block offset to a point in an earlier section that looks exactly the same — its position inside the section, its facing and its velocity all kept — so the body walks on and sees nothing happen. The loop holds until a party-wide story condition is met (an object found, a lever used, the n-th crossing counted), and from then on the plane is just floor. The spike proved the mechanism on the pinned server and a human walk on a client found no visible jump; this spec makes it a declared region the compiler proves seamless, the route proof proves escapable and the bot exercises.
- **Research**: §2 is this spec's own measurement, taken on the pinned server with the harness's bot (`tools/spike-seamless-loop/`, raw readings in `observations.json`). Every other rule is marked **cited** (a line of the tree at `c0f22c51`, a reading in the spike's `observations.json` at `2bbb1f28`, a measurement in §2, or a constitution rule) or **authored** (this spec chooses). No fact here was taken from a wiki. What a client renders between two frames is not measurable by a bot and is said so where it matters (§4.1, §10).
- **Numbers**: spec `0086`. DW codes `DW0945` (slab), `DW0946` (tiling), `DW0947` (open view), `DW0948` (body), `DW0949` (gate), `DW0950` (unmet), allocated by the planner; `DW0311`, `DW0542` and `DW0921` widen their messages and take no new code. `loops[]` is a stage-5 surface change; `dsl_version` does not move, as handed by the planner.
- **Non-goals**: hiding the move from a **witness** — a second player watching the mover sees a body jump, and §5.4 says why the engine does not try to hide it; a loop between two **areas** (areas sit 256 blocks apart; a loop is inside one place); a loop that returns a body to a place that looks **different** (that is a teleport — a gather or, under spec-0083, a link — and it has its own proofs); any fog surface of its own (a place's fog is spec-0080's `atmosphere`, and §4.3 reads it; this spec adds no attribute and no paint); any new harness constant (§6); mobs that chase a looped body (every non-fixture body in the slab is moved, §3.3, and nothing more is promised about a mob's pathing); the `on_cross` bundle addressing the mover alone (§3.5 dispatches it from the server source, like a trap).

## 1. The thing, and the object it belongs to

**Cited** (the spike at `2bbb1f28`, `tools/spike-eldritch-visuals/dw-eldritch-spike/data/dwe/function/corridor/`). Station 4 is a 90-block corridor with a 6-block repeating pattern of pilasters and lanterns; `corridor/tick` runs every tick `execute if score #loops dwe.s matches ..5 as @a[x=4095,y=64,z=4218,dx=2,dy=2,dz=0] at @s run function dwe:corridor/loop`, and `corridor/loop` is `tp @s ~ ~ ~-12` plus a counter and three story writes keyed on the count (cracked walls at 2, half the lamps gone at 4, a sound at 6). The spike's `observations.json` recorded six loops, six position packets each `(0, 0, -12)` with flags `255`, and a release after the sixth. That is the whole mechanism: a one-cell-thick selection slab polled on the tick, a relative `tp` of each body found in it, a party-wide score that stands it down.

**The object is a region, and the behaviour is standing.** The capability — *a body that enters this volume is returned by this offset* — acts on the body that enters a volume, which is what `lethal_volumes[]` acts on (*a body that enters this volume dies*). Neither is an event on the story's timeline: nothing completes, nobody is addressed, the world does not change; the volume simply has a property, every tick, for whatever is in it. So the loop is declared where the lethal volume is, as a sibling element **`loops[]`** at stage 5, with the same region type (`StealthZone`, resolved through the one `Plan::zone_box`), the same tick-polled emission shape and the same class exclusions (**cited**: `tools/ci/check-capability-ownership.py` check C refuses a private twin of the region type; `DW0545` names the fixture class).

Two placements were considered and rejected. **A trigger** (`triggers[]`, `on: cross{region}`, `once: false`, with a relative-teleport effect): a trigger's bundle is addressed to the party or to the presser (`TriggerAudience`) and dispatched as a story event; a loop moves bodies one at a time, including non-players, and addresses no one — and the seamlessness proof (§4) is a property of the region-plus-offset pair, which a compiler would have to recognise by pattern-matching a trigger's effect list, the private-re-implementation shape CLAUDE.md names. **A `teleport` effect with a relative `to`**: an effect fires at a point in the DAG and the route proof reads it as a leg (spec-0083) or a gather; a loop holds over time and the proof reads it as a seal (§5). What the loop *does* share with `teleport` it takes from the same sites (§5.5).

## 3. The surface

### 3.1 `loops[]`

**Authored.** Stage 5 gains `loops[]`, one entry per loop:

```
{ id: loop/<kebab>,
  region: { anchor, extent },           // the slab a body crosses — the one StealthZone
  to:     { anchor, offset? },          // where the slab's own anchor cell lands — the one Mark
  requires_flags?, forbids_flags?, requires_state?,   // the one gate: the loop HOLDS while it is open
  counts?: <state id>,                  // a party datum raised by one on every move
  on_cross?: [ <effect>, … ] }          // the dungeon's answer to a move, run from the server source
```

`region` is the anchor-centred box every other region is (`anchor ± extent`), with the slab rule of §4.2. `to` is a mark, and the loop's **offset** `d` is derived: `d = cell(to) − cell(region.anchor)`, a whole-block vector by construction, because both ends are cells. A creator therefore writes the landing as a judgement about the world — *the anchor of the fourth bay lands on the anchor of the second* — and never types a vector the compiler could have computed (CLAUDE.md: a creator types judgements only). `DW0897` applies to `to` as it applies to every mark.

### 3.2 The gate is the release

**Authored**, over the cited gate every gate consumer carries (`requires_flags`, `forbids_flags`, `requires_state` — `EnvTrigger`'s doc: *the third field of the one gate, carried by every gate consumer*). A loop **holds** while its gate is open and **stands down** while it is shut. Nothing is inverted: `forbids_flags: [flag/the-bell-found]` is a loop that ends the moment the flag is set, which is `forbids_flags`' documented meaning (*suppressed while any listed flag is set*); `requires_flags: [flag/the-inscription-read]` is a hall that only becomes endless after a beat; `requires_state: [{state: state/hall-crossings, op: at-most, value: 5}]` on the loop's own `counts` datum is the spike's sixth-crossing release. A loop with no gate term at all holds forever and is refused at the document (`DW0949`): a corridor nobody can leave is not a mechanism, it is a soft-lock spelled out.

**The release is a fact about the party.** Flags are campaign state (cited: `EnvTrigger::forbids_flags` doc, *by any player — flags are campaign state*; spec-0018). A `requires_state` term in a loop's gate must name a `party`-scoped datum; a `player`-scoped one is `DW0949`, because a release one player holds and another does not is a party split into a looped half and a free half, and §5.4 refuses that shape where it is entered rather than proving around it.

### 3.3 Who is moved

**Authored**, from the cited selector rule of `teleport` (*the selection is total over bodies*, `tag=!dw_fixture`, `DW0545`) and of `lethal_volumes[]` (`tag=!dw_cutscene` on the player selector). Every tick the loop holds, every body in the slab is moved by `d` — players and content bodies alike, each on its own, from its own position — except an engine fixture (`dw_fixture`) and a player watching a cutscene (`dw_cutscene`). A player is moved on **their own** crossing and nobody else's: the semantics are per body. A mob that follows a player into the slab is moved too, which is the only reading under which a chase survives the loop.

### 3.4 `counts`

**Authored.** `counts` names a `state[]` datum of `party` scope; the loop adds one to it on every move, before `on_cross` runs. A `player`-scoped datum here is `DW0949` for the reason of §3.2. Absent, no datum is written and nothing in the emission reads one.

### 3.5 `on_cross`

**Authored.** `on_cross` is an effect root — the eighth in `delvewright_dsl::effects`' enumeration, entered there and nowhere else (**cited**: `tools/ci/check-effect-roots.py`, *no source file may enumerate the campaign's effect roots by hand*). It runs on every move, after the body is moved and the count raised, under `Audience::Scheduled` from the server command source: a loop's answer is the dungeon acting, as a trap's payload is (**cited**: compiler.md's trap row, *a trap is the dungeon firing at the party, not at whoever touched it*), so an effect that names `@s` has no body and the scheduled-bundle rule of compiler.md §4 applies unchanged. Each effect's own `when` guard is how a write is keyed to a count (*crack the walls at the second crossing* is `when: [{state: state/hall-crossings, op: equals, value: 2}]`). A `teleport` effect inside `on_cross` is refused (`DW0949`): the body was just moved by the loop, and a second move in the same tick is two carries with one position.

## 4. Seamlessness — what the engine proves

**The claim the engine makes** is one sentence: *at the moment a body is moved from `p` to `p + d`, everything the body could see from `p + d` is what it could see from `p`, cell for cell*. §4.1 says why that is the claim; §4.2–§4.6 are the checks, each a set the engine already computes.

### 4.1 Why the view is the whole of it

**Cited** (§2): the server keeps the body's position inside its cell, its facing and its velocity; the client receives one relative update with nothing to reset. So the body's own motion does not hitch, and the only thing that can betray the move is the **world**: a cell that looks different from the landing than it looked from the slab. In the spike the far end of the hall stood 12 blocks nearer after each move and the spike's own record named it as what could betray the illusion; it was not seen on the one client walk because the far end was dark. Darkness is not a proof — the client's brightness setting is the player's — so the engine proves the view **closed**, by geometry or by an atmosphere's fog (§4.3; a fog end is a biome attribute the engine paints and reads, not a client setting), and **identical** inside the closure (§4.4, §4.5). A creator who wants a straight hall either gives the place a fogged atmosphere (spec-0080) whose fog end falls short of the hall's far end, or jogs or turns the hall inside the periodic span; that is the craft of every seamless-loop corridor in level design (a seam goes where the eye cannot be), and here it is a refusal rather than advice.

### 4.2 The slab

**Authored**, from §2's measurement. `region` is a **slab**: exactly one axis of `extent` is the crossing axis `a`, and `d` is non-zero along `a` — a body is returned *through* the plane it crossed. The slab's thickness along `a` is `t = 2·extent[a] + 1` cells, and the whole slab is carried out of itself by the move: `|d[a]| ≥ t`, else a moved body is still in the slab next tick and is moved again every tick for as long as it stands there. The slab is thick enough for the poll: a body's reach along `a` is its hitbox extent on that axis (`metrics::PLAYER_WIDTH` 0.6 for x or z, `PLAYER_HEIGHT` 1.8 for y; vanilla selects on hitbox intersection), and the fastest displacement per tick along `a` must be less than `t + reach`, so that no body passes through the slab between two polls — the horizontal bound is §2.1's sprint-jump tick (`0.5878`) and the vertical bound is the fall law's limit (`3.92`), both held in `dsl::metrics` beside `JUMP_REACH` with the rig named as their instrument. So a horizontal slab may be one cell thick, and a vertical slab under a fall must be at least **three** (`3 + 1.8 = 4.8 > 3.92`; two cells, `3.8`, is under the limit, and one cell was measured to miss). A horizontal slab one cell thick passes (§2.1: a window of `1.6` cells against `0.59` a tick, so sprint-jumping, the fastest horizontal locomotion, is caught 8 of 8); a vertical slab is judged against the fall law's limit (§2.1), and the rule takes that number, not the fastest tick one fall happened to reach. Every slab fault is `DW0945`: not a slab (two or three axes thick, or `d[a] = 0`), a move that does not clear the slab, a slab thinner than the poll needs along `a`, a slab that intersects another loop's slab or landing, a slab that intersects a `teleport` volume or a lethal volume's keep-out, or a slab whose cells are not all passable (a body must be able to be in it).

**Cited**, `DW0542` widened: a compiler-placed affordance inside the slab — an interact objective, a click trigger, a bonfire, a checkpoint seat, a shortcut unlock, a disarm — is refused by the same code the teleport volume uses, with the loop named: the body would be moved off the thing it reached for.

### 4.3 The periodic span, and a closed view

**Authored**, from the cited sightline predicate. Let the **landing slab** be `region + d`. The **eyes** are: for every cell of the landing slab a body can stand in, the player's eye (`metrics::PLAYER_EYE_HEIGHT` over its feet) at the cell's centre and at the four points `±0.3` toward each horizontal corner — the hitbox's own extent, so a body against a wall is in the sample. A cell is **in sight** of an eye when the segment from the eye to the cell's centre, or to any of its eight corners, is walked by `walk_cells` and meets no cell `World::blocks_camera` holds for before it — the one definition of *stopped by geometry* the compiler has (cited: `blocks_camera`'s doc, *a second predicate for it would be a second opinion about what a fence does to a view*). The player's eye height is used rather than `has_line_of_sight`'s 1.5 mob eye, because the viewer here is a player; it is the same traversal.

**Fog closes what geometry does not** (cited, spec-0080 §2.2 and `horizon::camera_weight` at `33ac8e68`): the client does not read fog from the biome at the camera; it reads every `visual/` attribute through a Gaussian kernel over the 4-cells within `BLEND_REACH` (12 blocks) of the eye, a linear mean for a distance, and `camera_weight(map, eye, biome)` is that kernel's weight for one biome, ported from the client's bytecode and held against the client's own readings. So each eye has a **fog end**: the kernel-weighted mean, over every biome the kernel reads at that eye, of that biome's `visual/fog_end_distance` — an atmosphere's declared value for its painted cells, and the attribute's default (1024) for a biome that declares none, the horizon's included. A cell farther from an eye than that eye's fog end is **closed to it**: the fog is whole there and nothing behind it is seen. The biome map is read as the configuration leaves it (a `set-atmosphere` repaint reaching the span is a write of §4.6). This is the one model spec-0080 already measures with (its *atmosphere reach* line reads the same eye through the same function); nothing here reads a biome by itself.

The **periodic span** `S` is grown, never declared: it starts as the box of the slab and the landing slab, and while any cell on the box's boundary shell that is not itself camera-blocking is in sight of an eye **and nearer to that eye than its fog end**, the box grows by one cell on that face — sight that reaches an open cell on the edge of the box, inside the fog, reaches past it. It stops when no open boundary cell is so seen (the view is **closed**, by geometry, by fog, or by both) or when the box has grown `R` cells from the landing slab on some face (`R` a named constant, 128: the campaign's render horizon is not the engine's to know, so the bound is the engine's and reported). The **visible set** `V` is every cell of the final box in sight of an eye and nearer than its fog end. A box that reaches `R` is `DW0947`, naming the loop, the eye, its fog end, the open boundary cell and the face — the creator closes the view by turning or jogging the corridor, by putting a door, a grille or a pillar across the line inside the span, or by giving the place an atmosphere whose fog end the eye reads whole. A box that grows above the built volume into open sky is an open view for the same reason: a roof is part of what a corridor looks like, and the sun does not move with the body but the roofline's edge does. A straight hall therefore compiles under a fogged atmosphere whose fog end falls short of its far end from every eye, and is refused without one; a hall whose paint ends within twelve blocks of an eye reads its fog mixed with the default (spec-0080 measured a hall painted over its own play space at 55.8% of its atmosphere, a fog end of 467 where 26 was declared) and is refused by the number, which the message prints.

### 4.4 Identical blocks

**Authored.** For every cell `c` in `V`: `block(c) = block(c − d)`, compared as full block states on the assembled `BlockMap` (the same states `light::emission` reads). The comparison runs over the world as the route's configurations leave it (§4.6). A mismatch is `DW0946`, naming the loop, up to six differing cells with both states and the count, and the configuration — the prescription is to make the two sections the same, never to shorten the view.

### 4.5 Identical light

**Authored**, over the cited light model (`crate::light`, a lower bound on the game's: *the emitter table never overestimates*). For every cell `c` in `V`: `light(c) = light(c − d)`, read from `light::relight_over` at the campaign's darkest reachable sky (`light::darkest_effective_sky`) and at its brightest, both. The model is a function of the blocks within fifteen cells and of the sky above, so with §4.4 holding it fails only where something outside `V` — a lamp round a corner, a hole in the roof over the next bay — lights two sections differently; that is exactly a difference a player sees as a brighter wall and the engine as a number. Reported under `DW0946` with the cell, both levels and which sky.

### 4.6 Writes, volumes and bodies inside the span

**Authored**, from the cited region model. The route passes through configurations (`region_state_at`, the same enumeration `DW0921` judges per configuration); in each, every runtime write reaching `S` — a `fill-region`, `clear-region`, `set-block`, `open-way`, a gate's seal, a timed gate's phase, and the loop's own `on_cross` writes — is applied to the comparison world first, and §4.4–§4.5 run again. A write that cracks every wall of the span tiles; a write that removes one lamp does not, and is refused in the configuration it first breaks (`DW0946` names the write and its root). A **declared volume** that intersects `S` tiles or is refused: a lethal volume's keep-out (`metrics::keep_out_box`) and a `teleport` volume must each be equal to their own image under `d` inside `S`, else `DW0946` names the volume — a pit the player sees in one bay and not the next is the frame jump by other means, and a pit that catches a body in the landing but not in the slab is the danger-is-visible rule broken (spec-0062, `DW0891`). A **compiler-placed body** (an NPC, a trigger body, a seated wave, an actor, an item display, a shop marker) whose cell lies in `S` is `DW0948` naming it: a body has an identity the move cannot repeat, so the span holds none, and a figure that *appears* mid-loop is placed by an `on_cross` effect outside `V` or summoned after the release. Spawn eggs and drops are not modelled and are named in §10.

### 4.7 Spec-0080, whichever lands second

**Authored.** This spec declares no atmosphere and paints nothing; it reads what spec-0080 paints. If spec-0080 lands first, `compiler::loop` judges each boundary cell through `horizon::BiomeMap` and `horizon::camera_weight` as they stand, and criterion 4's fog cases are built with `areas[].atmosphere` / `boxes[].atmosphere`. If this spec lands first, the span closes by geometry alone, every eye's fog end is the attribute's default (1024, so no cell inside `R` is closed by fog), and spec-0080's landing adds the fog reading at the one site in `compiler::loop` where a boundary cell is judged, with criterion 4's fog cases landing in that pull request. In either order there is one biome map, one kernel and one eye.

## 5. The proof, and spec-0083

### 5.1 The slab is a gated seal

**Authored**, over the cited seal model (compiler.md, *Runtime region solidity*: a leg is routed with a region forced solid iff its causally-latest write among the leg's ancestors is a fill, cleared iff a clear). A loop's slab is a region the route proof treats as **solid while the loop holds and clear while it stands down**, read per leg from the gate's state at that leg (`flags_at` for the flag terms; the `statepath` replay `DW0879` already runs for the numeric terms, widened as spec-0083 §3.3 widens it — *a gate the path has open here*). No write object is invented: the seal's state is the gate's state, and the gate is evaluated by the one `Flow` replay every other gate is.

So the route proof **shows the release is reachable and that after it the loop ends** without a new proof: a leg that must cross the slab routes only in a configuration where the gate is shut, and the gate shuts only by writes the forced path performs (spec-0051: *an unguaranteed firing may seal a region and may never open one*). A forced path whose leg crosses a holding slab is `DW0311`, whose message widens to name the loop, the gate term still open at that step and the step the gate was read at; the walk prescription is dropped from that message because a walk was never the way.

### 5.2 The exercise step

**Authored.** A loop that holds on the forced route is **exercised**: at the first path step at which the party stands inside `S` on the slab's approach side while the loop holds, `build_critical_path` splices a `loop` step (§6) in front of the next step. The step crosses the slab `times` times, where `times` is the smallest number of crossings after which the loop's gate shuts by the writes of its own `counts` and `on_cross` alone, read from the `statepath` replay, or `1` when the gate does not shut that way. The writes those crossings perform are credited to the path as **forced** — the party is forced through the step — so a release counted on the sixth crossing is a release the proof sees, and the `on_cross` writes of crossings one to five are the configurations §4.6 checks. The step's `transport` is its landing cell, so `positions_of` marks the leg out of it `transport_before` exactly as a crossing and a spec-0083 link are marked: **one enumeration of visited positions for every consumer**, and the leg after the step begins at the landing.

A loop the forced route never meets while it holds is `DW0950`, an advisory naming the loop and the step at which its gate was first read shut: a declared mechanism nobody is made to experience is reported, not refused, because a corridor that is endless only until a thing is found elsewhere is a design.

### 5.3 Branches, pockets and populations

**Authored.** `check_branch_path` reads the same slab state per branch, so a branch that releases the loop by a different flag is proven on its own flags. `check_bodies_can_leave` (`DW0921`) judges each configuration with the slab solid or clear as that configuration has it; a body inside `S` while the loop holds is not in a pocket, because the approach is open behind it and the slab returns it to the approach — the route cells of that configuration are inside `S` whenever the forced route is, which is `DW0921`'s existing rule for a room the story shuts the party into. The **put-at** roots of `DW0891`'s population gain every landing-slab cell, and the **stands-at** roots gain each exercise step's landing cell (spec-0083 §3.8's two sets, if that spec lands first; `lethal::population_roots` otherwise — in either case one list, extended, never a private copy).

### 5.4 Per-player semantics, and why nobody is stranded

**Authored.** The release is party state (§3.2), so there is no configuration in which one player's slab holds and another's is clear: when the gate shuts it shuts for every body, and a body inside `S` at that moment walks on through the slab like any floor. Before the release, every body is returned on its own crossing to a place it can walk forward from, so no body is ever behind a wall it did not see. What a **witness** sees is stated and not hidden: a party member in sight of the mover sees a body vanish at the slab and reappear twelve blocks behind, because the mover's entity position is absolute to everyone else. Moving every body inside the span together was considered and **rejected**: it keeps relative positions only among bodies already past the landing, pushes a body in the approach back out of the span by `|d|` on every crossing someone else makes (unbounded, since nothing stops the leader looping again), and turns a per-body region into a party event with a leader. The engine's answer is the design's: a loop is one body's experience, and a party that wants it seamless walks it one at a time, which the demo level shows.

### 5.5 What this shares with spec-0083, and what it does not

**Authored.** Both specs describe a body **carried** by the engine, and both read the party's position through `positions_of` and its `transport_before` mark — the one enumeration (spec-0083 §2.6) — so a loop's exercise step and a link's trigger step look the same to every proof that reads positions. Both take their volume from `Plan::zone_box` and their landing from a `Mark`; both exclude `dw_fixture`; both widen `DW0542`'s territory; both feed the put-at and stands-at roots. They differ in **what the proof does with the carry**: a link is a teleport the route proof *takes* when a walk fails (0083 §3.4); a loop is a teleport the route proof *refuses to take* — a seal — until the gate shuts, and then nothing is taken because nothing moves. Where spec-0083 names a step's `transport` the destination of a link, this spec names it the landing of a loop; the field is one field with one meaning, *where the party stands after this step*, and the harness reads it once. If spec-0083 lands first, this spec's §5.3 roots and §6 parser keys are added to its lists; if this spec lands first, spec-0083 adds to these. Neither depends on the other's branch.

## 6. The bot

**Authored**, over the cited harness (`executor.ts`: `onForcedMove` records the position after a server-forced move and resets the pathfinder only at `TRANSPORT_JUMP_BLOCKS` (64); mineflayer sets `bot.entity.position` before emitting `forcedMove`). `critical-path.json` and every `branch-path-<branch>.json` gain a step shape:

```
{ "action": "loop", "loop": "loop/<id>", "pos": [x, y, z], "cross": [x, y, z], "offset": [dx, dy, dz], "times": N, "transport": [x, y, z] }
```

`pos` is a standable cell in the approach, inside `S`, on the route; `cross` is the slab cell the route passes through; `offset` is `d`; `transport` is `cross + offset`, the landing cell, which is the same for every crossing because a body is always moved from inside the slab. The bot walks to `pos`, then sets a walk goal `2·t` cells past `cross` along `a`, waits for a `forcedMove` whose delta from the position of the physics tick before equals `offset` within `1e-3` on each axis (§2: measured exactly on 10 of 10), calls `stopPathfinding()` on it so the stale goal does not walk the body into the slab again, walks back to `pos`, and repeats until `times` moves are seen; a forced move with any other delta, or no move within the walk's own timeout, fails the step naming the loop, the delta seen and the count reached. `TRANSPORT_JUMP_BLOCKS` is not consulted and not lowered: a loop's move is identified by its exact delta, not by its size. The parser (`critical-path.ts`) accepts `loop` with exactly these keys and refuses a zero `offset`, `times < 1`, or a `transport` that is not `cross + offset`, as a `CriticalPathParseError` naming the step. After the release the bot crosses the slab inside an ordinary walk leg and the executor expects no forced move there, which is the existing behaviour; a forced move during a plain walk whose delta equals a declared loop's offset fails that walk naming the loop, because it means the proof's configuration and the game's disagree about the gate.

## 7. Emission

**Authored**, in the shape of `lethal_<id>`. Per loop, one named function `loop_<id>` whose body is: the count (`scoreboard players add #party dw.s_<local> 1`, when `counts` is declared), the move (`tp @s ~<dx> ~<dy> ~<dz>` — vanilla's relative form, all three coordinates relative, which is what makes every component of the position packet relative, §2), and a call into the generated `on_cross` bundle function run from the server source (`execute run function <ns>:loop_<id>_cross`), so the body's own move and the dungeon's answer are two functions with two audiences. One tick line: `execute <gate as the one gate formatter emits it> as @e[<box>,tag=!dw_fixture,tag=!dw_cutscene] at @s run function <ns>:loop_<id>`, the box from `emit::box_selector_args` over `Plan::zone_box`. The count is raised before the move so an `on_cross` guard reads the crossing it belongs to. Absent `loops[]`, nothing is emitted and every campaign is byte-identical.

## 10. What the engine does not check, by name

**Authored.** Each is a limit the build prints in `loop-gate.json` under `unchecked`, so a reader of the ledger cannot mistake silence for a proof. (1) **A client frame.** Whether a client shows anything at the seam is a client fact; the engine proves the packet is relative and the view identical, and the demo level is where a person looks. (2) **Particles and positional sounds.** A particle alive in `V` at the move, or a sound playing from a fixed point inside `S`, is at an absolute position and shifts by `d` for the mover; a `play-sound` at the listener is unaffected. The engine does not trace what is playing at the tick of a crossing. (3) **Items on the ground and projectiles.** Not placed by the compiler, not modelled; they move with the slab like any body and otherwise stand where they fell. (4) **A witness** (§5.4). (5) **Chunk streaming at the far ring** (§2): the same ring a walk streams, never in a corridor's view; a client with a render distance below the server's is not modelled.
