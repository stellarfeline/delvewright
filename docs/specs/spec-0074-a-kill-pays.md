# spec-0074: A kill pays — what happens each time a body of a fight is killed

- **Status**: Draft — ready for implementation
- **Ground**: written against engine `509ebc58` (`origin/main`), read only — `Wave`, `Actor`, `EncounterTier`, `EnvTrigger.once`, `TrapReset` in `crates/dsl/src/stages.rs`; `EffectRootKind`, `EffectRootOwner`, `EffectRootSite` in `crates/dsl/src/effects.rs`; `wave_tag`, `wave_total`, `wave_area`, `reseat_waves`, `undefeated_reseat_waves`, `reseat_actors` in `crates/delvec/src/compiler/plan.rs`; `hostile_actors` in `crates/delvec/src/compiler/combat.rs`; the `k_<wave>` advancement, `k_reward_<wave>`, `wave_reseat_<wave>`, `actor_restand_<id>`, `emit_despawn_actor`, `root_audience`, `state_holder`, `emit_kill_reward_packtests`, `pin_dummy` in `crates/delvec/src/compiler/emit.rs`; `docs/reference/compiler.md` (`waves[].respawns_on_rest`, the `kill`/`spawn-wave` emission row, the `bonfire` emission row, `DW0503`, the executor contract, the PackTest batch model); the gallery (`gallery/quests.json`, `gallery/probes/`, `gallery/README.md`); `tools/ci/gallery_units.py`. The one-authority removal helper `removal_lines` is on an open branch and is named here as the shape every compiler removal takes, not as a surface this spec depends on.
- **What it is for**: a creator can say what happens **each time a body of a fight is killed** — grant a currency, play a sound, set a flag — and can choose whether a body that comes back after a rest pays again. Today a fight pays only through `on_objective_complete` of a `kill` objective, once, when the whole wave is down; nothing fires per body, and a creator whose economy loses currency permanently on a second death (a forfeited stake) has no way to author earnings that can be repeated, so the economy can only deflate.
- **Research**: §7 is this spec's research record. Every rule below is marked **cited** (the record, a vanilla behaviour the engine already emits and proves on the pinned server, or a constitution rule requires it) or **authored** (this spec chooses).
- **Numbers**: no ADR (no settled decision moves). **Three DW codes**: `DW0913` for §8.1 (a bundle on a body no player can be credited with killing), `DW0914` for §8.2 (`every-kill` on a fight that never comes back), `DW0915` for §8.3 (no `fires` on a fight that does come back); `DW0916` was handed to this spec and is **not consumed**. **`dsl_version` moves by one minor step** (ADR-0024): §2 adds a field to two object classes, so a document that carries it stops parsing under the previous number; the value is typed in `crates/dsl/Cargo.toml` and nowhere else — `tools/lib/version_sites.py` refuses a second statement of it, this page included.
- **Non-goals**: paying for a death nobody was credited with (§3, §9); a per-mob-entry bundle (§2); a `paid_to` field (§5); a drop-table or item-loot surface (`drops[]` already exists, spec-0021); a kill *count* objective (a wave's `kill` objective already completes on its last body); any change to what the countdown, the census or the floor gate measure.

## 1. The finding

The engine already knows the moment a player kills a body of a wave, and already runs a function for it. Every wave gets an advancement `k_<wave>` on vanilla's `minecraft:player_killed_entity` criterion over the wave's tag, whose reward `k_reward_<wave>` runs **as the killing player**: it decrements the countdown, adds one to the credited-kill ledger `#wcred_<wave>` the floor gate reads, and revokes itself so the next kill grants it again (`docs/reference/compiler.md`, the `kill`/`spawn-wave` emission row). That function is a per-body, per-kill event with an acting player, and nothing a creator writes can reach it.

The two fight classes the engine has are the wave (`dw_wave_<id>`) and the actor a campaign `unleash-actor`s (`dw_actor_<id>`, `hostile_actors`). Both are re-seated by a rest: a `respawns_on_rest` wave whether or not it was beaten, a billed `elite`/`boss` wave and every hostile actor while they still stand (spec-0016 §1, the undefeated re-seat). A rest is therefore the one place where "the same body dies twice" is a real question, and today no surface can answer it.

Currency is already a `state[]` datum with a `scope` and, when named, a visible purse (spec-0031, spec-0032). The vocabulary to pay exists; the event to pay on does not.

## 2. Where the bundle lives — a property of the fight, on both shapes a fight takes

**Rule (authored).** `on_kill` is an optional property of `waves[]` and of `actors[]`, one shared type on both:

```
on_kill: { fires?: "first-kill" | "every-kill", effects: [ <quest effect>, … ] }
```

`effects` is an ordinary effect list (every verb `on_objective_complete` accepts, gated per effect by `when` as everywhere else) and is non-empty (an empty list is the exported schema's `minItems: 1`, refused as `DW0100`). `fires` is §4. Absent ⇒ no bundle, and emission is byte-identical to today for every campaign that declares none.

**Why these two classes.** The bundle acts on *a body being killed*, and the two classes whose bodies the engine fields under a tag it owns are the wave and the actor — the same pair that carries `tier` (spec-0023), the same pair the undefeated re-seat is defined over, the same pair `equipment` is one shape on. One type on both, so the two surfaces cannot drift.

**Why not on `waves[].mobs[]`.** A mob entry is a *kind* of body (`entity`, `count`, `equipment`, `drops`); the wave is the encounter, and the kill advancement, the countdown, the census and the re-seat all see the wave, never the entry. A per-entry bundle would need a per-entry body tag the engine does not emit. A fight whose bodies should pay differently is two waves spawned by one beat — the spelling the re-seat and the `kill` objective already use for *a boss with adds*.

**The bundle is effect root R9** (`EffectRootKind::OnKill`, owner `EffectRootOwner::OnKill` carrying the fight — a wave or an actor, one enum for the pair). It is enumerated by `for_each_effect_root` (visited only where declared, so `unbound_roots` tells the truth about a campaign with none), lives in the quests stage, **runs with an acting player** (`runs_with_acting_player` = true, `root_audience` = `Audience::Solo`), and is **optional** in the completability model in the same sense `on_death` is: nobody is forced to be credited with a kill (§3), so a `close-gate` inside it registers its seal only and no firing is assumed. Every walker the effect-root matrix (`tests/effect_root_walkers.rs`) asks is asked about R9 by the exhaustive match; `plan::wave_area` resolves a `spawn-wave` inside an `on_kill` exactly as it resolves one inside a `sequence`; `DW0360` seals its anchors; the l10n inventory keys its text as `wave.<id>.on_kill.<i>…` / `actor.<id>.on_kill.<i>…`.

## 3. When it fires — a credited kill, and nothing else

**Rule (cited — vanilla's own credit).** The bundle fires when the game credits a player with the body's death: the `minecraft:player_killed_entity` criterion, which vanilla grants when *a player is the source of a mob being killed* (§7). A kill by the player's own hand or projectile is credited to that player. Reaching the bundle *is* the credit; the engine adds no second detector.

**The acting player is the credited player** (`@s` in the reward function, the same executor `k_reward_<wave>` and every `bf_<i>`/`shop_<i>` reward already run under). A `player`-scoped datum written in the bundle is that player's; a `give-item` lands in that player's inventory; a `narrate` is heard by that player (`Audience::Solo` — the `on_death` shape, so one kill is not narrated to four people).

**A death nobody is credited with fires nothing** (authored, on the vanilla rule). A body that falls, burns, drowns, walks into a lethal volume, is cut down by another mob or is killed by a command has no credited player, grants no advancement and runs no bundle — the same rule under which vanilla drops it no experience. The countdown still clears (the per-tick recount, unchanged), the `kill` objective still completes, and `count − present − credited` on the census still counts it as the world's kill. What this costs is stated honestly: vanilla's *experience* rule is wider than the trigger's (a body that dies within five seconds of a player's hit drops experience whatever killed it, §7), so a body a player knocks into a pit pays nothing here where it would have dropped orbs. The trigger is the only per-kill event vanilla exposes as a function; the engine exposes it as it is and invents no wider one (§9).

**A compiler removal can never fire it** (cited — structural). Every removal the compiler performs — `wave_reseat_<wave>` (both re-seat kinds), `actor_restand_<id>`, `unleash_<id>`'s puppet swap, `despawn-actor` in either style — ends in `/kill` from the server command source, which has no causing entity; `player_killed_entity` is granted to nobody, so no reward runs. This is proven live (acceptance criterion 3), not argued from the command tree.

**Ordering** (cited from the emitted reward). Within one credited kill: the countdown is decremented, the credited ledger is incremented, **then** the bundle runs, then the advancement is revoked. The `kill` objective completes on the next `tick`, so the bundle of the last body fires **before** that objective's `on_objective_complete`; a creator who wants a beat on the whole fight falling keeps it on the objective, and a beat per body on `on_kill`.

## 4. `fires` — whether a body that comes back pays again

A fight **comes back** when the engine re-seats it after the party has met it: a `respawns_on_rest` wave (`reseat_waves`), an undefeated `elite`/`boss` wave (`undefeated_reseat_waves`), a hostile actor (`reseat_actors`) — all three only where the campaign declares a `bonfire` — and any fight whose `spawn-wave` / `unleash-actor` beat lies in an effect root that can fire more than once (a trigger with `once: false`, a trap with `reset: rearm`). One derivation, `Plan::fight_comes_back`, enumerates those sites through `for_each_effect_root` and is the sole authority for both refusals of §8.

**Rule (authored).**

| `fires` | what it means |
|---|---|
| `every-kill` | every credited kill of a body wearing the fight's tag fires the bundle, however many times the fight is re-seated |
| `first-kill` | over the whole delve the fight fires **at most once per body it seats** — `wave_total` times for a wave, once for an actor; a re-seat does not renew the count |

`first-kill` is a **budget over the fight**, not an identity over seats, and that is the exact definition: a re-seated body is a fresh entity (`kill` then `spawn_<wave>`), the engine carries no seat identity across a re-seat, and the bundle is one list for the whole fight, so the only fact a player can observe is how many kills of this fight have paid. A party that kills two of three, rests and clears the three is paid once more, whichever of the three falls first. The ledger is `#kf_w_<wave>` / `#kf_a_<actor>` on `dw.sys`: seeded `0` in `setup`, incremented as the **first line of the bundle function** so it counts firings and nothing else, reset by no spawn, re-seat or rest, and stated nowhere on the wire (it is not a census field; the census's `credited` already counts credited kills per seating and this counts payments per delve — two facts, two holders).

**`fires` is a judgement, typed where it is one and nowhere else** (authored; spec-0071's rule). Where the fight comes back, `fires` is **required** (`DW0915`) — the engine does not decide for a creator whether their economy can be farmed, in either direction. Where it does not come back, the two values coincide, so `fires` is **optional**; `first-kill` may be stated (it is true) and `every-kill` is refused as inert (`DW0914`) — a declaration that binds to nothing is the defect class this compiler always makes loud. A creator who later adds a bonfire is told, per fight, which judgement the bonfire has just created.

## 5. Who is paid — the datum's scope, never a field on the hook

**Rule (cited — spec-0031's object-class rule).** The bundle runs as the credited player. **Who receives** a payment is a property of the thing paid, not of the kill: an `add-state` on a `player`-scoped datum pays the killer (`@s`), on a `party`-scoped datum pays the party once (`#party`). Both are one verb through `state_holder`, already emitted that way under every `Solo` root. There is no `paid_to` on the hook: it would be a second authority for the datum's scope, and a hook that names a recipient a `player` datum cannot honour is `DW0503`'s class of finding restated.

The three shapes a creator can write, and what each does with four players:

| the creator wants | how it is written | what happens |
|---|---|---|
| the one who lands the blow keeps it | `add-state` on a `player` datum | the killer's purse moves; the others' do not |
| a shared purse | `add-state` on a `party` datum | one write to `#party` per kill |
| every player paid per kill, each into their own purse | — | not a shape this hook has: a `player` datum written from a solo root is the killer's, and a per-player write addressed to the whole party is a different verb shape, declined in §9; a creator who wants it today pays the `party` datum and prices from it |

## 6. The vanilla primitive, and what is emitted

**Waves** (cited — reuse). The advancement `k_<wave>` and reward `k_reward_<wave>` already exist for every wave. A wave with `on_kill` emits one more function, `on_kill_w_<wave>` — ledger increment, then the bundle under `Audience::Solo` — and `k_reward_<wave>` gains one line between the ledger and the revoke: `function <ns>:on_kill_w_<wave>` for `every-kill`, `execute if score #kf_w_<wave> dw.sys matches ..<N−1> run function <ns>:on_kill_w_<wave>` for `first-kill` (N = `wave_total`). A wave without `on_kill` emits `k_reward_<wave>` byte-identical to today.

**Actors** (authored — the same shape one class over). An actor with `on_kill` emits an advancement `ka_<actor>` (`player_killed_entity`, `{Tags:["dw_actor_<id>"]}`), a reward `ka_reward_<actor>` (`function <ns>:on_kill_a_<actor>` or its `matches ..0` guard, then `advancement revoke @s only <ns>:ka_<actor>`), and `on_kill_a_<actor>`. The tag is on the caged puppet too; a puppet is `Invulnerable` and cannot be the subject of a credited kill, and a `vulnerable: true` actor a player kills before any unleash *has* been killed by a player — it pays. Emitted only for actors that declare the bundle, so every campaign without one is byte-identical.

**Runtime holders.** `#kf_w_<wave>` / `#kf_a_<actor>` are runtime state written by an emitted campaign function, so under the PackTest batch model a template may drive or reset them and never suffixes them; `setup` seeds them to `0` beside `#wcred_<wave>`.

**Determinism.** Function bodies, advancement JSON and the `setup` seeds are emitted in content order; two builds are byte-identical (ADR-0006).

## 7. Research record — how the reference games pay a kill, and what vanilla credits

Sources and their standing: the Minecraft Wiki (`minecraft.wiki/w/Advancement_definition`, `…/Commands/damage`, `…/Experience`) is CC BY-NC-SA — **ideas only** (ADR-0013); Fextralife pages (`darksouls.wiki.fextralife.com/Bonfire`, `darksouls2.wiki.fextralife.com/Soul_farming`) are under Fextralife's custom licence — **ideas only**; `hollowknight.wiki/w/Bench_(Hollow_Knight)` and `diablowiki.net/Multiplayer` are community wikis — **ideas only**; Steam community threads on Elden Ring co-op are player reports, not a record, and are marked as such. Each says, in its own words:

- **Vanilla, the trigger.** `minecraft:player_killed_entity` *triggers after a player is the source of a mob or player being killed*; its conditions are `entity` (the body that died, an entity predicate — `nbt` matching is what `k_<wave>` already uses) and `killing_blow` (a damage-type predicate). `rewards.function` runs a function on grant. → **Adopted** as the one event (§3); its reward executor is the granted player, a fact the engine already relies on for `k_reward_<wave>`, `bf_<i>` and `shop_<i>`.
- **Vanilla, the experience rule.** *A mob does not drop experience orbs unless it dies within five seconds (100 game ticks) of an attack registered as a player hit (including tamed wolves, player-thrown fireballs, and TNT)*; a mob that *falls off a cliff* drops none. → **Adopted in principle** (an uncredited death pays nothing, §3), with the difference between the two credit rules stated as a cost (§3) — the wider rule has no function-running form in vanilla.
- **Vanilla, `/damage`.** `damage <target> <amount> [<damageType>] [by <entity>] [from <cause>]`; `by` *specifies the entity who dealt the damage*, `from` *the cause of the damage (for example, the skeleton that shot the arrow)*. → **Adopted** as the PackTest's way to deal a credited blow (acceptance criterion 3): `by <player>` with no `from` makes the player the source; the bare form credits nobody.
- **Dark Souls (Fextralife, *Bonfire*).** *Resting at a Bonfire will respawn all Enemies, excluding Bosses, mini bosses, certain non-respawning enemies, and NPCs*; the respawned enemies drop souls again, which is the basis of soul farming. Dark Souls II caps how many times an enemy respawns; Dark Souls III does not. → **Adopted as the pair the creator chooses between** (§4): `every-kill` is the Dark Souls I/III economy, `first-kill` is a budget. The Dark Souls II *finite respawns* shape is a cap on the re-seat, not on the payment, and is not adopted (§9).
- **Hollow Knight (*Bench*).** *Resting at a bench respawns defeated enemies in rooms other than the one you are sitting in*, and they drop Geo again — the game's own farming loop. → the same shape as Dark Souls; adopted through §4.
- **Elden Ring co-op (player reports, Steam).** The host's rune award per kill is reduced by a share and each cooperator receives that share — every player present is paid something, each into their own purse. → **Not adopted as a mechanism**; the engine's answer is §5 (a `player` datum pays the killer, a `party` datum pays the pool) and a split is a creator's arithmetic on those two, which the engine has no standing to fix.
- **Diablo III (*Multiplayer*).** *Gold and items are not shared*: the gold that drops for one player is that player's; experience is shared among nearby players. → the per-player purse is §5's first row; a shared pool is its second.
- **Minecraft Dungeons (Fextralife, *Multiplayer*).** *Emeralds are not shared and will vary from player to player*. → the same as Diablo III.

What the record does not answer, and this spec authors: whether the first-kill count is a seat identity or a budget (§4, a budget — the engine has no seat identity across a re-seat); where `fires` is required (§4); that a compiler removal never pays (§3, proven live).

## 8. Refusals

1. **A bundle on a body no player can be credited with killing** (`DW0913`): `on_kill` on a wave no beat spawns (the wave resolves no area — `wave_area` is `None`, the same fact that leaves it without machinery), or on an actor that no `unleash-actor` names and that is not `vulnerable`. Prescription: spawn or unleash it somewhere, mark the actor `vulnerable`, or remove the bundle. The spec-0034 rule: a declaration is a claim, and a claim nothing can exercise is refused.
2. **`every-kill` on a fight that never comes back** (`DW0914`): `fires: every-kill` where `Plan::fight_comes_back` is false. The two values coincide there, so the declaration binds to nothing. Prescription: state `first-kill` or nothing, or make the fight come back (a bonfire and `respawns_on_rest`, a tier, or a repeating spawn beat) — the message names which of those the fight lacks.
3. **No `fires` on a fight that does come back** (`DW0915`): `on_kill` without `fires` where `Plan::fight_comes_back` is true. Prescription: state `first-kill` or `every-kill`; the message names the site that makes the fight come back (the bonfire and the field, or the repeating root).

All three are raised at `delvec validate`, where the field is entered, before any build. 8.1 is validation-tier (exit 1) in `dsl::validate` over the two static facts it reads (the unleash set is `combat::hostile_actors`'s definition, restated nowhere). 8.2 and 8.3 read `Plan::fight_comes_back`, which needs the collected checkpoints, and are raised from the compiler side at validation tier (exit 1) — the `DW0343` precedent for a check that needs a fact the DSL crate does not carry — and are one pair over one predicate: a fixture that reds 8.2 with `every-kill` reds 8.3 with `fires` removed and passes with `first-kill`, in every combination, or the pair is defective. Every code owes a test (`tools/ci/check-dw-codes.py` holds the reference and the code set bidirectionally). `DW0916` is unused.

## 9. Declined, with the reason

- **Paying for an uncredited death** (the party paid when a body falls into a pit) — vanilla has no per-death trigger; the recount is a per-tick delta over a tag, with no body, no killer and no way to honour `first-kill`; a `DeathLootTable` that drops a marker item to be swept up is a hack at the NBT→compiler boundary. Excluded until vanilla provides a primitive.
- **A `paid_to: killer | party` field** — §5; a second authority for the datum's scope.
- **A default for `fires`** — §4; the engine deciding whether a creator's economy can be farmed is a design decision in a primitive.
- **A per-seat first-kill identity** — §4; the engine has none across a re-seat, and a budget is the only observable.
- **A finite re-seat count** (Dark Souls II) — a property of the re-seat, not of the payment; a later spec on `respawns_on_rest`, if wanted.
- **A per-player party-wide write from the bundle** (§5, third row) — a new verb shape (`add-state` addressed to `@a`), not a property of this hook; the `party` datum covers the shared-pool case today.
- **Reading the `killing_blow`** (pay more for a headshot, an arrow, a fall the player caused) — no reference game in §7 does it; a second surface for one event, without a design that needs it.
- **Paying through `dropped_by`** (the token-drop mechanism) — a drop is loot the player must walk to and pick up; a payment is a write. Two mechanisms for two experiences; a creator who wants a walk-to-it reward already has `drops[]`.

## Acceptance criteria

Each criterion is checked against the tree at `509ebc58`: the surface it names exists (or is named as owed by the implementation), and none is satisfied today.

1. **Surface.** `delvec schema --stage all` exports `on_kill` on `waves[]` and `actors[]` as one type with `fires` (two variants, `first-kill` and `every-kill`, no default) and `effects` (`minItems: 1`); `dsl_version` is one minor step over `main`'s. A campaign that declares no bundle builds byte-identical to the previous engine (`gallery/baseline/` differs only where a bundle was added and `delta.json` attributes every row).
2. **Emission tests** (`crates/delvec/tests/emit.rs`, beside the wave and actor emission tests; the R9 arm in `tests/effect_root_walkers.rs`): a wave with `every-kill` emits `on_kill_w_<wave>` whose first line increments `#kf_w_<wave>` and whose remainder is the bundle under `Solo`, and `k_reward_<wave>` calls it unguarded after the credited-ledger line and before the revoke; a `first-kill` wave of three bodies emits the `matches ..2` guard; an actor with a bundle emits `ka_<actor>` (`player_killed_entity` over `dw_actor_<id>`), `ka_reward_<actor>` and `on_kill_a_<actor>`; `setup` seeds each ledger to `0`; a `player` datum in the bundle writes `@s`, a `party` datum writes `#party`; a call-graph test (`crates/delvec/tests/call_graph_integrity.rs`) asserts every reward names a function that exists. Perturbation: change `fires` and the guard appears or disappears; change the amount and the `scoreboard players add` operand moves; remove the bundle and `k_reward_<wave>` is byte-identical to `main`'s. Build twice, byte-equal (ADR-0006).
3. **Generated PackTests** on the pinned server, in the family `emit_kill_reward_packtests` belongs to, **one set per fight that declares a bundle** (the `DW0811` rule: a per-object body is driven per object), driven with the real generated functions and a PackTest fake player (`pin_dummy`). The implementing change first **measures** on the pinned server whether `damage <body> <n> minecraft:player_attack by <fake player>` grants `player_killed_entity` to the fake player, and writes the answer in its commit body; if it does, that command is the credited blow below, and the negative claims use the bare `damage <body> <n> minecraft:generic`; if it does not, the credited blow is `execute as <dummy> run advancement grant @s only <ns>:k_<wave>` (the drive `emit_kill_reward_packtests` uses today) and the negative claims stand as written, since nothing grants. Per fight:
   - `kill_pays_<f>`: seat the fight, deal one credited blow to one body: `#kf_<f>` is 1 and the bundle's first `add-state` holder moved by its amount (asserted where the bundle carries one on a `party` datum; otherwise the ledger alone);
   - `kill_pays_uncredited_<f>`: seat it, kill every body with no player credited, run `tick`: `#kf_<f>` is 0 and the countdown is 0 (the `verb_kill_uncredited` claim, extended to the payment);
   - `kill_pays_removed_<f>`: seat it, run the real `wave_reseat_<wave>` / `actor_restand_<actor>` / the emitted `despawn-actor` lines over the standing bodies: `#kf_<f>` is 0 — the compiler-removal claim of §3, proven by the removal that exists for that fight;
   - `kill_pays_across_rest_<f>` (only where the fight comes back through a bonfire): credited-kill every body, run the real `bonfire_rest_<i>`, credited-kill every body again: `#kf_<f>` is N for `first-kill` and 2N for `every-kill`, N the fight's body count — the two modes proven on one shape, so the test can tell them apart.
   The gallery's generated PackTests run in the required `tier 2` job (spec-0039 §8.11), so these run on every PR.
4. **Diagnostics.** `DW0913`, `DW0914`, `DW0915` each have a red fixture in the tests of the crate that raises them, naming the fight; the 8.2/8.3 pair has the three-way fixture §8 demands (`every-kill` reds 8.2, absent reds 8.3, `first-kill` passes, on a fight that comes back; and on one that does not, `every-kill` reds 8.2, absent and `first-kill` pass). `tools/ci/check-dw-codes.py` is green and `docs/reference/compiler.md` carries the three rows; `DW0916` appears in neither.
