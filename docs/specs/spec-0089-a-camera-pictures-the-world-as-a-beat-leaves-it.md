# spec-0089: A camera pictures the world as a story beat leaves it — a showcase camera states the critical-path step it is taken after, the engine renders the configuration the proofs read from a world it writes itself, and the caption names the beat

- **Status**: Proposed
- **Ground**: written against engine `2316b1c6` (`origin/main`), read only — `Camera` / `CameraSheet`, `world_scene`, `resolve_sky` and `emit` in `crates/delvec/src/compiler/view/camera.rs`; `ChunkyScene`, `WorldRef`, `loaded_extent`, `chunk_list` in `compiler/view/scene.rs`; `resolve_world` and `ViewCommand::{Cameras, Scene, Panorama, PlaceCamera}` in `compiler/view/cli.rs`; `run_cameras_preview` in `main.rs`; `RegionState`, `World::region_state_at`, `with_region_state`, `world_while_next` in `compiler/nav.rs`; `RegionEvent`, `RegionWrite`, `collect_region_events`, `Plan::gate_fired_before`, `Step`, `objective_steps` in `compiler/plan.rs`; `PovShot` in `compiler/render_plan.rs`; `assembled_blocks` and `BlockMap` in `compiler/assembled.rs` / `blockstate.rs`; `validation/world-save.sh`, `validation/render-shots.sh`; `tools/ci/check-gallery-coverage.py`; the gallery's `design.json`, `design/cameras.json`, `quests.json`, its probes, and its build at this revision (`critical-path.json`, `render-plan.json`, `validation/leave-proof.json`, the emitted functions). The integration branch `integration/stranding-capabilities` at `edab67d9`, read for `RegionState::blocks_over`, `RegionState::laid`, `RegionEvent::laying`, `Configuration`, `path_configurations` and `configurations_along` in `compiler/nav.rs` / `plan.rs`, and for spec-0086 §4.4 and spec-0088 §5. The pinned Chunky core `chunky-core-2.5.0-SNAPSHOT.474.g156e2bb` (`versions.toml` `[render]`), read as a class list and string table. The rig `tools/spike-post-beat-camera/ at 6573392e4818` and its README, which is this spec's measurement record.
- **What it is for**: a picture of a delve can show only the world at load. `delvec build` writes no world; `validation/world-save.sh` boots the build once, waits for the datapack to finish placing, and copies the save; `delvec cameras` renders that save. So a demo whose point is what a beat changes — a lid that opens, a repaint, a collapse — has had its after-picture made from a second, hand-edited world, and nothing proves that world is the one the proofs walked. This spec closes the gap at the record: a showcase camera states the critical-path step it is taken after, and the engine renders the world as the region model holds it at that configuration — one block map per configuration, the same function the per-configuration proofs read — from a world the compiler writes. The caption names the beat.
- **Research**: §2 is the research record. Each rule below is marked **cited** (a source in the tree at the ground revision, the pinned core read as bytes, a published format page, a constitution rule, or a measurement in the rig's README) or **authored** (this spec chooses).
- **Numbers**: `spec-0089` is the only number taken here. Refusals that are rules of the camera record are raised under the record's own code, `DW0721`, as spec-0069 §7 and spec-0079 §6 did; §6 lists the shapes so the reader can see each is a record rule. One diagnostic is new, allocated `DW0955` (`DW_CAMERA_STEP_WORLD`), the gate that holds the compiler-written load world to a server-written save (§5.4). `dsl_version` does not move: the camera record is not a stage document, and no stage document changes shape. `render-plan.json` moves (§8).
- **Non-goals**: a camera taken *during* a beat (a lid half-open, rubble in flight) — the model holds configurations between steps, not ticks; entities in a frame (§6.1); the text of signs and the patterns of banners (§6.2); a `set-atmosphere` repaint in a frame where the paints are not yet in the tree (§6.3); a frame's sky, which stays spec-0079's (§6.4); the review frames' and the panorama's world source, which stay the server save in this spec and are named as the next caller of the writer (§8); a world save for the player-facing server (ADR-0004, ADR-0010: the shipped image carries the datapack and stamps its own world).

## 1. The defect, and the object it belongs to

**Cited** (the tree at `2316b1c6`). `world_scene` writes `world.path` into every showcase scene from `resolve_world`, which accepts a directory holding `level.dat` and at least one region file and defaults to `<build-dir>/world`, "where `validation/world-save.sh` writes it". That script boots the delve image, polls `#placed dw.sys` over rcon until the datapack reports placement finished, flushes, stops and copies the save — and it stops there, before any beat, by construction: its readiness signal is the placement sentinel. `render-shots.sh` refuses without that directory, and its header says why: Chunky renders a missing world as an empty sky at exit 0. So every scene the engine emits — showcase camera, POV review frame, panorama — is a scene of the world at load, and no command in the tree can produce any other.

The proofs do not live at load. `World::region_state_at` yields, for an arrival at critical step `s`, every runtime region write whose firing step is a causal ancestor of `s`, latest write per region winning, with the world's own load-time seals entered as step-0 fills; `with_region_state` gives the leg its world; `DW0921` enumerates the distinct states the path passes as *quest configurations*. On the gallery at this revision that enumeration counts **4 configurations** over a 12-step path (`validation/leave-proof.json`, `configurations`, measured: `delvec build gallery` from this tree). The integration branch carries the half this spec needs and `main` does not: `RegionState::laid` (per region, the causally-latest forced write and the block its emitted command writes) and `RegionState::blocks_over(base) -> BlockMap`, "the one derivation of a configuration's block map, for whoever asks", which `DW0891` reads to decide whether a caught cell is shown (spec-0088 §5) and spec-0086 §4.4 reads to compare an endless corridor's two sections. `Configuration::blocks` is that function on the enumeration.

**The object the step belongs to is the picture's camera, not the command and not the design row.** A design row (`design.json`, spec-0061) states what an approved image shows and the sky it was drawn under, and it is written at the design stage, before a quest plan exists; a critical-path step exists only once quests are expanded and built, and the camera record is written *against a build* (spec-0070 §5's argument for why its refusals sit at the build). A flag of `delvec cameras` is typed per run and recorded nowhere, so the frame it produced could not be re-asked for from the repository (spec-0079 §1's argument, **cited**). So the step is a field of the camera, beside `sky`, stated once in the record (**cited**: CLAUDE.md, *a capability belongs to the object class it acts on*; spec-0069 §4.1, *the record is the only format of a showcase camera*). A review frame's step is not typed at all: it is a derivation of the leg the shot stands on, and §8 says what the plan writes for it.

## 2. Research record

### 2.1 What a server-written save holds that a block map does not

**Cited** — the rig's `census` over the gallery's save written by `world-save.sh` from this tree's build (README, *What the server's save holds at load*): 1453 chunks stored, 151 of them `minecraft:full` and the rest proto-chunks holding no block; 5939 non-air cells, all inside the layout box, in 27 distinct block states; **0** fluid states with a non-zero `level`; 3 `gravel`; block entities `chest` 2 and `trapped_chest` 1; entities `interaction` 16, `item_display` 4, `villager` 2, `mannequin` 1, `item` 1; light arrays on 84 and 6 of 34,872 sections; every region timestamp non-zero. A block map holds the first four rows and none of the rest. Of what it does not hold, §2.2 says what the renderer would have drawn.

### 2.2 What the pinned renderer reads

**Cited** — the pinned core's class list and string table (README, *What the pinned core reads*):

1. Its chunk loader names `sections`, `block_states`, `biomes`, `palette`, `data` and `entities`, and names neither `BlockLight` nor `SkyLight`. The core lights a scene by path tracing and reads no stored light, so a world written without light arrays loses nothing in a frame.
2. Its world loader names `level.dat`, `Data`, `SpawnX`, `SpawnY`, `SpawnZ`, `version`, `region` and `Dimension`.
3. Its entity classes are armour stands, players, paintings, heads and skulls, signs, banners and hanging signs, books, lecterns, campfires, beacon beams, lily pads, coral fans, spore blossoms, a sculk sensor's amethyst, flame particles, and seven mobs (sheep, pig, chicken, cow, mooshroom, squid, copper golem). There is **no class** for `mannequin`, `villager`, `interaction`, `item_display`, `text_display` or `item`. Every entity kind the engine summons — a skinned NPC is a `mannequin`, a plain one its `base_entity`, a fixture an `interaction` with an `item_display`, a stake an `item` — is one the pinned core draws from no world, server-written or not. The entities the census found (§2.1) are not in today's frames either.
4. Of the block entities, chests render from their block state (the core's chest is a block model), and signs, banners, heads and lecterns are the block-entity classes of item 3: their text, pattern, profile and book come from block-entity NBT, which a block map does not carry (§6.2).

### 2.3 A minimal written world renders as the server's

**Cited** — the rig's `rewrite` and `compare` (README, *A minimal world is the same cells*; *The pinned core renders the minimal world as the server's*). The server's save was written back holding, per chunk, `DataVersion`, `xPos`, `zPos`, `yPos`, `Status: minecraft:full` and per section `Y`, `block_states` and `biomes`, zlib, every timestamp zero, only the 6 chunks holding a block: 589,824 cells written and read back equal, 32,768 bytes, and two rewrites of one save byte-identical. A 94-byte `level.dat` holding only `Data{DataVersion, LevelName, SpawnX, SpawnY, SpawnZ, version}` loaded. Rendered by the pinned core from the gallery's `hall-exterior` camera at the draft budget, the minimal world's frame sits inside the noise floor of the server's own frame rendered twice (luminance rms **2.095** and **2.094** against a floor of **2.102**), and the one perturbation only a block map could make — the visible block swapped for gold — moves the rms to **33.798**, so the comparison sees a block state move and the equal rows are not a comparison that sees nothing. A torch-lit interior at 128 samples had a floor of 34.2 and discriminated nothing; the exterior carries the measurement.

### 2.4 The world format

**Cited** — minecraft.wiki, [*Region file format*](https://minecraft.wiki/w/Region_file_format) and [*Chunk format*](https://minecraft.wiki/w/Chunk_format): a region file `r.<x>.<z>.mca` is an 8 KiB header — 1024 location entries of 3 bytes sector offset and 1 byte sector count, then 1024 timestamps "for the last update of said chunks" — followed by 4 KiB sectors; a chunk payload is a 4-byte length, a 1-byte compression scheme (1 GZip, 2 Zlib, 3 uncompressed, 4 LZ4, 127 custom) and the bytes; a section's `block_states.data` packs indices at "the minimum amount of bits required to represent the largest index in the palette, and then set to a minimum size of 4 bits", "not packed across multiple elements of the array", and "if only one block state is present in the palette, this field is not required and the block fills the whole section"; `biomes` is the same shape over 4×4×4 quarts. The rig's writer is these rules and nothing else, and §2.3 is the evidence the pinned core reads what it writes. `DataVersion` **4671** is what the pinned 1.21.11 server wrote (§2.1), and is the value a written chunk carries.

### 2.5 What the model holds per configuration

**Cited** — the integration branch at `edab67d9`. `RegionEvent` carries, beside the write's class, `block: Option<String>` — "the block this write lays, as its emitted command writes it (spec-0088 §5)": a fill's block, `None` for a clear or an unseal, and for a `collapse` its settled `falling_block` and its `then_floor` where declared, set by `RegionEvent::laying` at the one site that collects region events. `RegionState::laid` keeps, per region, the causally-latest **forced** write and that block; `blocks_over(base)` lays each over a clone of the assembled `BlockMap`, inserting the block or removing the cell. An unforced write is not laid — "a block a beat nobody has to play lays is no signal the party is shown" — and a write whose block the model does not know (a world-load seal: the bytes already hold it) leaves the bytes as they are. `configurations_along` walks a path's steps in its own step space under its own ancestry and keys each distinct state by the first step arriving under it; `path_configurations` is that over the critical path. **On `main` at `2316b1c6` none of `laid`, `laying`, `blocks_over`, `Configuration` or `path_configurations` exists.** This spec's world is `blocks_over`'s block map and no private copy; the implementation cannot compile against `main` until those land, which is the ordering, made structural by construction rather than stated in prose (**cited**: CLAUDE.local.md, *an ordering that exists only as prose is not an ordering*).

## 3. The surface: `after` on a camera

**Authored.** `design/cameras.json` gains one optional field per camera:

```json
{
  "after": { "step": "obj/clear-the-muster" },
  "answers": "concept/bay-after-the-muster",
  "exposure": 1.0,
  "fov": 60.0,
  "height": 900,
  "name": "east-bay-after-the-muster",
  "pitch": 14.0,
  "pos": [21.5, 70.0, 26.5],
  "source": "estimated",
  "spp": 300,
  "width": 1600,
  "yaw": 225.0
}
```

1. **`after` is `{step, path?}`.** `step` is the id of a step the exported path carries, in the vocabulary `critical-path.json` already speaks: an objective id (`obj/<id>`, the step that proves it, `plan.objective_steps`) or a trigger id (`trigger/<id>`, the `Step::Trigger` that performs it). Never an index: a step index moves when a rest is spliced or a quest reordered (spec-0016 §1's splice; `compiler.md`, *every `fire_step` index … count `plan.critical_path`*), and a camera must survive a rebuild that moves nothing it photographs. `path` names the exported path the step is on — absent, the critical path; otherwise a branch id the build's `validation/branch-plan.json` declares, whose own `branch-path-<slug>.json` is the step space and whose own ancestry is the one `configurations_along` is asked under (§2.5: "a configuration is its region state, whichever path reaches it"). A camera on a branch path pictures what a party on that branch sees; a step reached only there is refused on the critical path by name (§6).
2. **Absent means at load.** A camera with no `after` renders the configuration before step 1 — every world-load seal in place, no beat fired — which is what every camera in every record renders today. "At load" has no id and cannot be stated: the step before the first is not a step.
3. **A step after which no block moves is refused.** Where `blocks_over` for the stated step yields the load map byte for byte, the field is a derivation typed where a judgement belongs — a picture of nothing different, which goes stale in the other direction the moment a beat is added. The refusal names the camera, the step, and the first step of that path after which the map does move, or says the path moves no block at all (**cited**: CLAUDE.md, *every input to a surface is either a creative judgement or a procedural derivation … an error is refused where it is entered*; spec-0079 §3.3's precedent for a stated sky equal to the row's).
4. **The record's writer takes it.** `delvec place-camera` gains `--after <step>[@<path>]`, parsed as the id and an optional path, refusing anything else; `--candidates --pick` copies the candidate's `after` verbatim; `--bracket` writes each candidate with its camera's `after`. A hand camera fired in the running game after the party has played the beat is written with the `after` the agent names in chat — the overlay cannot read the quest state, and a stamp carrying it would be a second authority for which step the party is at.
5. **Key order stays alphabetical**: `after, answers, exposure, …`. The field-list test in `crates/delvec/tests/hand_camera.rs` holds `compiler.md`'s list to the structs in both directions; `after` enters that list.

## 4. The configuration a camera stands in

**Authored, on §2.5's cited parts.** For a camera stating `after: {step: X, path: P}`, with `i` the index of `X` in `P`'s step list:

1. **The state is the one arriving at `i + 1`** — `region_state_at(events_P, i + 1, ancestor_P)`: every forced write fired at a step that is a causal ancestor of the step after `X`, which is the state the proofs route the leg leaving `X` under (`world_while_next`). For the last step of a path, `i + 1` is past the end, and `gate_fired_before` already treats an arrival past the last objective as preceded by every objective and trigger step on the path (**cited**, its doc comment): the end state. The camera therefore sees `X`'s own firing — a beat fired *on completing* `X` is credited to the leg after it — which is the reading "taken after step `X`" means.
2. **The bytes are `blocks_over`** over the assembled `BlockMap` the build already holds (`assembled_blocks`, the same map `--preview` rasterises and the light model reads). Nothing is derived twice: a cell this picture shows solid is a cell the route proof could not walk through at that step, and a cell it shows open is one the proof could. An unforced write is not laid, as the model does not lay it (§2.5); the binding line counts them (§7).
3. **A collapse shows settled.** The configuration after a `collapse` beat holds the debris where `DW0445` settled it and the `then_floor` where declared (§2.5), not the ceiling that fell: the picture is of the room the party walks back into, which is what spec-0088 §5 judges and what the demo level needs.
4. **One function, every caller.** The configuration's block map for a camera, for a review frame (§8) and for every proof is `blocks_over`; `grep` over `crates/delvec/src/` finds no second site that lays a `RegionEvent`'s block over a `BlockMap`.

## 5. The world the engine writes

**Authored, on §2.3 and §2.4.** A Chunky scene names a world directory and nothing else will do (§2.2 item 2), so the engine writes one.

### 5.1 What is written

`compiler::view::world::write(blocks: &BlockMap, biomes: &BiomeMap, dir: &Path) -> WrittenWorld`: under `dir`, `level.dat` and `region/r.<x>.<z>.mca`, and nothing else. Per chunk holding at least one cell of the map: `DataVersion` (the pinned game's, a constant beside the command tree — 4671 for 1.21.11, §2.4), `xPos`, `zPos`, `yPos`, `Status: minecraft:full`, `sections[]` for the sections holding a cell, each with `Y`, `block_states{palette, data}` and `biomes{palette, data}` packed by §2.4's rules; every region timestamp zero; zlib at one fixed level; chunks in index order, sectors contiguous. `level.dat` is §2.3's minimal compound with the spawn at the campaign's start cell. No light arrays, no heightmaps, no entities, no block entities, no `block_ticks`, no `fluid_ticks` (§2.2 says why none is missed; §6 says what is). The biome map is the build's own answer for which biome is where — today the horizon's ground biome, and `horizon::biome_map` once spec-0080 is in the tree (§6.3).

### 5.2 Determinism

Two writes of one block map are byte-identical (ADR-0006 — **cited**; the rig measured it on a server save, §2.3): no timestamp, no wall clock, a fixed compression level, palettes in first-seen order over a `BTreeMap` iteration, the data array packed from that order. `WrittenWorld` carries the sha-256 over the region bytes in file order, the chunk count and the cell count, and `delvec cameras` prints them (§7). A written world is therefore hashable where the server's save is not — `world-save.sh`'s header, *nothing may hash it*, stays true of the save and false of this.

### 5.3 Where it lives, and the flag that goes

`delvec cameras` assembles the world as `--preview` already does (it reads the campaign and `--prefabs`), computes the configuration of every camera it emits, writes one world per distinct configuration under `<out>/worlds/<key>/` — `at-load`, or `after-<step>` with the path's slug appended for a branch — and names it in each scene by absolute path exactly as `resolve_world` names the save today, for the same reason (Chunky resolves the path against the rendering process's working directory). **`--world` is removed from `delvec cameras`**: a showcase frame has one world source, and a flag that could point it at a server save would be a second authority for what the frame shows (**cited**: CLAUDE.md, *a second bespoke field is the defect*). `tools/ci/check-skill-page.py` rule 4 holds the skill's `delvec cameras` lines to the pin's clap surface, so the page's hand-camera loop drops its `world-save.sh` step for cameras with the pin that carries this.

### 5.4 The cross-check

A measurement that is a deliverable is cross-checked by a second method sharing no configuration with the first (**cited**: CLAUDE.md, *Measurement doctrine*). The written load world and a server-written save are those two methods: one is the compiler's model, the other the pinned game executing the compiler's datapack. `tools/ci/check-written-world.py <build-dir> <written-world> <server-save>` reads both as the rig's reader does (one parse rule, the rig's module promoted to `tools/lib/anvil.py`), compares every cell inside `layout_aabb`, and prints the differing cells grouped by state pair with the count and the denominator. It runs in the gallery's whole-map-render job directly after that job's `world-save.sh`, and reds as `DW0955` on any differing cell except one of the classes it names and counts separately — a gravity block settled by the server, a fluid cell the server flowed, a connection state (`fence`, `wall`, `iron_bars`, `stairs` shape) the server re-derived on a block update — each class a measured count, never an allowlist of cells. On the gallery at this revision the census predicts zero in every class (§2.1: no flowing fluid, three gravel on the floor, every connection state authored in full by the template). A class that is non-zero is a finding about the model, not about the picture, and is reported with the cells. Nothing in the engine renders the server save for a showcase camera after this spec; the save is the instrument that checks the writer, and `world-save.sh` keeps its other callers (§8).

## 6. What a frame does not show, by name

**Authored, on §2's cited parts.** Each limit is printed on the binding line (§7) so a creator reading a frame knows what is absent by construction.

1. **Entities.** None — and none is lost: the pinned core draws no entity kind the engine summons (§2.2 item 3). A frame of the server's save shows the same empty floor where the NPC stands. A frame that must show a body is a render gap of a different class (a figure composited from the skin, as the catalog cards do), not this spec's.
2. **Block-entity content.** A sign's text, a banner's pattern, a head's profile, a lectern's book are block-entity NBT the map does not carry, and the pinned core draws them from it (§2.2 item 4). The written world leaves a sign blank and a banner plain. The prefab template holds that NBT and the compiler places the template, so carrying it is a derivation the writer *could* make; it is excluded here until a picture needs it, and the binding line counts the block entities the written chunks omit, read from the templates, so the count is a measured zero on a campaign that places none.
3. **A repaint by a beat.** The written world's biomes are the build's biome map. Where `set-atmosphere` paints a volume by a beat (spec-0080, on the integration branch and not on `main`), a configuration's biome map is the load map with every forced paint credited by the same latest-write rule as a block, derived by the same function family; until the paints are in the tree the binding line prints `biomes: at load`, and when they are, the writer takes the configuration's map and the line names the paints laid. A Chunky frame's sky and fog stay spec-0079's in either case (spec-0080 §5, **cited**).
4. **The sky.** The frame's sky is the picture's — the camera's `sky`, else its row's (spec-0079 §3) — and a `set-time` or `set-weather` cut fired before the step does not move it: the row is a judgement about the picture, and a picture of a beat at dusk drawn at dusk is right whatever the world's clock says. The binding line prints the configuration's clock beside the frame's sky where the two differ, so the disagreement is visible and chosen.
5. **A fluid's spread.** A `Flood` write lays its source cells and no spread (`RegionWrite::Flood`'s own note, **cited**), so a basin filled by a beat shows its written cells and not the flow the server would run; the camera shows exactly what the proof refused to walk, which is the point.
6. **An optional beat.** A write only an unforced root lays is not in any picture (§2.5). A creator who wants the trap sprung in frame makes the trap's beat forced on a path, or accepts that the picture is of the world the proofs guarantee.

## 7. Captions and the binding line

**Authored.** Every `delvec cameras` run prints, refused or not, beside the `answers:` and `sky:` lines spec-0070 and spec-0079 put there:

- per emitted camera — `after: <name> after <step> (step <i> of <n> on <path>): <c> cells moved from load, <u> unforced write(s) not laid, <b> block entit(ies) omitted; biomes: <at load | configuration>; clock: <as the picture | <time>+<weather> at this step>` — and for a camera with no `after`, `after: <name> at load`;
- per written world — `world: <key> <chunks> chunk(s), <cells> cell(s), sha256 <hash> -> <dir>`;
- a summary — `configurations: <k> written for <c> camera(s), <a> after a step, <l> at load`.

A record that states no `after` prints `0 after a step` and one world, `at-load`: a measured zero. **The caption names the beat.** Where a frame is shown to a person — the design-gate contact sheet, a demo level's README, a storybook — its caption says what the picture is taken after, in the player's own words (*after the muster is cleared*), never the id; `showcase-shots.md` §2b carries this rule beside its sky rule, and the storybook rule in the skill's hand-over page stands unchanged: a storybook shows exterior or starting-scene shots and no late-game place, so a post-beat frame reaches a storybook only where the beat is one the reader may see before playing. A frame's file name carries the key (`<campaign>_camera_<name>` is unchanged; the scene's `world.path` ends in the key), so a frame and its configuration cannot be separated in a directory listing.

## 8. The plan's shots

**Authored.** A review frame (`delvec scene`: a POV shot on a critical-path leg) stands in a configuration too — the leg's — and that configuration is a derivation, never typed. `render-plan.json` gains, on every `pov` shot, `after: {step, cells_moved}`: the step whose leg the waypoint lies on (`per_step` of `path_configurations`) and the cells its map moves from load. The plan **states** the configuration now; `delvec scene` keeps rendering the server save at load in this spec and prints `review frames render the world at load; <k> of <m> POV shots stand in a configuration other than load` — a measured limit, never a silent one — and is named here as the writer's next caller, together with `delvec panorama`, in a spec of their own that decides what a reviewer judges a leg's light by. The alternative, moving the three verbs in one change, puts the hour the owner spends at the visual-review step behind a world source nobody has looked at a frame from yet; the gallery's showcase frames are where it is looked at first (§9). The baseline moves by the new key on every POV shot and nothing else, attributed row by row in the commit that regenerates it.

## 9. The gallery, the probes, the demo level

**Authored**, against `gallery/` at `2316b1c6`: `design.json` has six rows, `design/cameras.json` seven cameras answering them, none stating a step; the build's path has 12 steps, and three of its completion functions carry runtime region writes (`complete_q_near_hall`: the main gate opened; `complete_o_clear_the_muster`: the east bay filled with `polished_andesite`, the west bay cleared, the main gate sealed again, a collapse of twelve falling `gravel` blocks; `complete_o_take_the_bone`: two courses of `stone_bricks`), measured by `grep` over the emitted datapack of this tree's gallery build.

1. **Bound elements.** `design.json` gains a seventh row, `concept/bay-after-the-muster` (drawn by `prefabs/gallery-generator --design` like the six), and `design/cameras.json` an eighth camera answering it, `east-bay-after-the-muster`, stating `after: {step: "obj/clear-the-muster"}` from a lens that sees the filled bay, the settled gravel and the sealed gate. `after.path` is bound by a second camera on a branch path whose configuration at its step differs from the critical path's — the gallery's `skipped` branch is the candidate — or, where no branch's configuration differs, refusal-proven by probe 3 below; the implementation measures which and says so in its pull request body.

## 10. Decisions put forward

Only what she would see; each shipped with its recommendation.

1. **One world source for showcase cameras (§5.3).** Recommendation: the compiler-written world for every showcase camera, at load included, with `--world` removed and the server save kept as the gate's instrument. What she sees: `delvec cameras` no longer needs a Docker boot before a draft, and every showcase frame is of the world the proofs read; a defect in the model shows in the picture instead of being hidden by the server's physics. The cost of the alternative — the written world for post-beat cameras only — is two world sources in one record and a load frame that can disagree with an after frame about a block neither beat touched.
2. **Review frames stay on the server save for now (§8).** Recommendation: yes, with the plan stating each shot's configuration and the limit printed. What she sees at the visual-review step: nothing changes in this round; a later round moves the POV frames onto the written world under their legs' configurations, and she judges the first such set on the gallery before a campaign's.

### 10.3 Settled

Both recommendations are adopted. **§10.1**: the compiler-written world is the single source of every showcase frame, at load included; `--world` is removed from `delvec cameras`; the server save is the instrument the CI cross-check (`DW0955`) reads. **§10.2**: review frames stay on the server save in this change; the plan states each POV shot's configuration and `delvec scene` prints the limit.

## 11. What the implementation measured, and where it departs

Each item is a measurement taken while building this spec, or a departure from the text above made because of one. A departure that asserts less than the text is named a loosening in those words.

1. **The world a picture starts from is the world as shipped, not the assembled map** (§4.2 amended). Measured against a `world-save.sh` save of the gallery: the assembly clears every gate region (the route model reads a gate through its seal), and the datapack's setup holds the gate's block there — 21 cells of bars the save held and the assembled map did not; 29 relight lanterns the datapack sets in `setup_finish`; a gated trap's tripwire the datapack removes while its gate is shut. So `RegionState::blocks_over` lays over `view::beat::picture_base`: `assembled::shipped_blocks` (the assembly, the sealed gates written back with their anchor's block, the relight fixtures last as `setup_finish` sets them — the loop's tiling reads the same function) less every gated trap's trigger shut at load. The claim §2.5 cites, that a world-load seal's block "the bytes already hold", is false of the assembled map; `DW0891` reads the assembled map and is not changed here (a finding about `DW0891`, recorded, not fixed in this change).
2. **The relight pass hung four lanterns under leaves that the pinned server drops** — found by the cross-check, fixed at the pass: a fixture is never mounted on `*_leaves`. Its direction: the light proof counted light the game never shows, so it could let a darker area ship.
3. **A section's `Y` is a byte** (§5.1 amended). The first render of a written world was an empty frame (rms 33.686 against the save's frame); bisected to the region file; the game and the pinned core write and read `Y` as a byte.
4. **States are completed with the pinned defaults** (§5.1 amended): the written palette carries every property the game would resolve on load (`BlockRegistry::default_state`), so a template that leaves `waterlogged` out is not a differing cell.
5. **The cross-check runs in tier 2, not the gallery job** (§5.4, criterion 6). The gallery's whole-map step boots no server (it writes a stub world); tier 2 builds the gallery and boots servers from the job's one verified fetch, so `world-save.sh` gains `--seed` and runs there, held to its own `is already installed`. **Two classes the text did not name**, each a measured count: leaves' `distance` and pane sides join the connection class as *re-derived* (states the server re-derives on a block update); and *clock* — a cell inside a gate region a timed gate's clock owns, whose blocks are the clock's phase at the instant the save is copied (17 and 18 cells on two saves of one build). Both are reported with their cells and do not red; this is a **loosening** of criterion 6's "reds on any other difference" by exactly those two classes. Measured on the gallery: 9666 cells compared, gravity 0, fluid 0, re-derived 50, clock 17, model 0.
6. **A collapse is not laid** — **a debt of criterion 2 and §4.3**. On `main` a `collapse` reaches the route proofs as `DW0445`'s settled debris, never as a `RegionEvent`, so no configuration lays its debris or its `then_floor`, and a frame after a collapse beat shows the ceiling standing. §2.5's description of `RegionEvent::laying` for a collapse described the integration branch, and did not reach `main`. Named on `compiler.md`'s list of what a frame does not show; the gallery's after-the-muster camera shows the filled bay and not the settled gravel.
7. **A `set-atmosphere` repaint is not laid** (§6.3). The paints are in the tree; the written world still takes the biome map at load, and the line says `biomes: at load`. Recorded, not built.
8. **Block entities omitted are counted from the written map's blocks of the kinds whose picture lives in block-entity NBT** (signs, banners, heads, lecterns), not read from the templates' NBT (§6.2). A **loosening**: a block of those kinds that carries no content is counted too.
9. **The remedy names a step a camera can state**: the first step after which a block moves *that the path carries once* — on the gallery the first moving step is `trigger/strike-the-sentinel`, carried three times.
10. **The step index counts `plan.critical_path`** (with the links the route proof takes spliced in), the region model's step space, not `critical-path.json`'s rows, which splice witness, rest and completion steps into the export (gallery: step 10 of 19, row 13 of 22).
11. **`after.path` is refusal-proven** (§9.1): over all 14 step ids on all three of the gallery's exported paths, every branch world's sha-256 equals the critical path's at the same step.
12. **Criterion 9's gallery assertions run in the gallery job** (`tools/ci/check-gallery-post-beat.py`), not in a cargo test, because a cargo test cannot build the gallery (the precedent of spec-0079's criterion 7). Its perturbations are the text's.

15. **The baseline moves `render-plan.json` by the POV shots' `after` and by `camera_eye_proof.showcase`** (criterion 9 named the first only): the count moves 7 → 8 because the record holds an eighth camera. ## Acceptance criteria

Each criterion is checked against the tree at `2316b1c6`: none is satisfied there; criterion 2's second sentence names the dependency the tree lacks.

1. **Surface.** The camera record accepts an optional `after: {step, path?}`; `delvec schema cameras` exports it; `hand_camera.rs`'s field-list test holds `compiler.md`'s list to the structs with `after` in it, in both directions; `delvec place-camera --after <step>[@<path>]` writes it, and `--candidates --pick` and `--bracket` carry it verbatim.
