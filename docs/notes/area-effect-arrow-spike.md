# Area-effect / non-block-breaking arrow — spike findings (Minecraft Java 1.21.11)

Status: **spike note**, measured 2026-08-11. Nothing here is implemented; no
engine, DSL, campaign or CI file changed. Rig: `tools/spike-area-effect-arrow/`
(`EULA=TRUE tools/spike-area-effect-arrow/run.sh`), raw observations committed
beside it as `observations.json`, and the pinned build's own registry dump as
`registries-1.21.11.json`.

Server: the pinned image digest (`versions.toml [images.base] mirror_of`),
`/version` = `1.21.11 / data 4671 / protocol 774 / pack_data 94.1`, vanilla, no
mods, superflat, difficulty hard, `mob_griefing` deliberately left **true** so
that no block-preservation result can come from a global gamerule.

**The question** (owner, 2026-08-11): can a datapack alone give the player an
arrow that on impact produces either (1) an explosion that damages but does not
break blocks, or (2) a splash-potion-style area effect — as an item that sits in
a chest as scavenged loot?

## Verdict — a PARTIAL primitive

**The trigger is real and intended. The payload is real and intended. The
BINDING is wrong for the item the owner named.**

1. **Both effects exist as first-class vanilla primitives, event-driven, no
   polling.** The enchantment effect component `minecraft:hit_block` fires on the
   tick a projectile lands, with the arrow entity as executor and the impact
   point as position. From there `minecraft:explode` with
   `block_interaction: "none"` gives a real explosion that destroys **zero**
   blocks, and `minecraft:run_function` gives an arbitrary function at the impact
   point — from which a vanilla `area_effect_cloud` is one command away.
2. **The enchantment must live on the LAUNCHER, not on the ammunition.** An
   arrow item carrying the enchantment does nothing, measured five ways. So "an
   arrow in a chest that anyone can pick up and shoot" is **not** what vanilla
   offers. What vanilla offers is a **bow in a chest**, plus — and this is the
   part that rescues the design — the arrow's own `custom_data` surviving to the
   impact, so one generic launcher enchantment can read which arrow was fired
   and branch. The scavenged item can be the arrow; the party must be holding an
   engine-issued bow when they fire it.
3. **`minecraft:explode`'s damage is a trap at the default offset.** Centred on
   the impact point — which for a downward hit is *inside* the block that was
   hit — it deals a flat **1.0 damage at every distance**, the fully-occluded
   floor of the vanilla explosion formula, while still playing the particle, the
   sound and the knockback. It looks like it works. Lifting the centre out of the
   block restores damage *exactly* equal to vanilla TNT — but the only correction
   vanilla exposes is a **fixed world-space `offset`**, and the impact normal is
   not available to the effect, so one authored arrow cannot be correct on both
   a floor and a ceiling.
4. **Therefore: the area-effect half (2) is clean and shippable. The
   explosion half (1) is shippable only if the engine computes the damage
   itself** from the same `hit_block` event (`run_function` → `/damage` in a
   radius), which is orientation-independent, has no line-of-sight term, and is
   the idiom `spec-0022` already established for traps. Using vanilla's own
   `explode` damage is the option that ships an invisible half-heart.

Nothing here needs polling, marker bookkeeping or scoreboard scanning, so the
no-hack rule does **not** exclude the feature. It does exclude the naive
authoring (`explode` at the default offset), and it constrains the DSL surface
to something keyed on the launcher.

## What settles the polling question before any measurement

The pinned jar's own `--reports` registry dump (`registries-1.21.11.json`,
regenerated by `run.sh` on every run) lists **58** entries in
`minecraft:trigger_type`. None of them is a projectile-landed trigger; the
closest, `minecraft:killed_by_arrow` and `minecraft:shot_crossbow`, fire on a
kill and on a draw. So the advancement route does not exist, and the *only*
alternative to what follows would be a per-tick scan of
`@e[type=arrow,nbt={inGround:1b}]` — the excluded shape.

The same dump lists `minecraft:hit_block` among **31**
`enchantment_effect_component_type` entries and `minecraft:explode`,
`minecraft:run_function`, `minecraft:apply_mob_effect`, `minecraft:summon_entity`
among **15** `enchantment_entity_effect_type` entries. Vanilla itself uses
`hit_block` exactly once, in `channeling.json` (trident → lightning), which is
the shape this spike copies.

## 1. Where the behaviour has to live (`a_binding`, `g_player_shot`)

Five summoned-arrow cases, each fired straight down onto a stone floor, counting
whether the `hit_block` function ran:

| # | `weapon` field (the launcher) | `item` field (the ammunition) | fired |
|---|---|---|---|
| A1 | enchanted bow | plain arrow | **yes** |
| A2 | plain bow | **enchanted arrow** | no |
| A3 | *absent* | **enchanted arrow** | no |
| A4 | *absent* | plain arrow | no |
| A5 | enchanted bow | enchanted arrow | **yes** |

And the same conclusion from four real bow shots by a live client:

| # | bow given | arrow given | fired | `ammo_matched` |
|---|---|---|---|---|
| B1 | `bow[enchantments={dwspike:mark:1}]` | `arrow` | **yes** | – |
| B2 | `bow` | `arrow[enchantments={dwspike:mark:1}]` | **no** | – |
| B3 | `bow[enchantments={dwspike:ammo:1}]` | `arrow[custom_data={dw_bomb:1b}]` | **yes** | **1** |
| B4 | `bow[enchantments={dwspike:ammo:1}]` | `arrow` | **yes** | 0 |

Rows B3 and B4 are the load-bearing ones. The arrow entity's `item` field
carries the fired arrow's components intact, so a single generic launcher
enchantment whose whole body is `run_function` can ask
`execute if data entity @s {item:{components:{"minecraft:custom_data":{…}}}}`
and do something different for a scavenged bomb-arrow than for the 63 ordinary
ones in the same quiver. Measured: `ammo_matched` is 1 for the tagged arrow and
0 for the untagged one, from the same bow, same function.

Execution context of `run_function`, measured: `@s` **is the arrow entity**
(`mark_exec_arrow` = 1, `mark_exec_player` = 0), and the function's position and
`execute at @s` agree to the micrometre — both at the impact point, e.g.
`[110.5, -60.00000999999975, 0.5]`.

**A dispenser cannot fire it, either way.** Dispenser-launched arrows have no
weapon item, so an ordinary arrow does nothing (expected) and — measured — an
arrow carrying the enchantment *on itself* also does nothing. An arrow entity
appeared in both trials, so this is a negative result, not a missed shot.

## 2. "Does not break blocks", measured (`b_block_damage`)

A solid 7×7×7 = **343-block glass box** (blast resistance 0.3) around the impact
cell, with a 4-cell shaft for the arrow. After the shot,
`fill … minecraft:glass replace minecraft:air` returns the air count, which is
the shaft plus whatever the blast took, and rebuilds the box in the same breath.

| enchantment | air cells before | after | **blocks destroyed** |
|---|---|---|---|
| `explode block_interaction=none` | 4 | 4 | **0** |
| `explode none`, `offset [0,1,0]` | 4 | 4 | **0** |
| `run_function` → `/damage` in a radius | 4 | 4 | **0** |
| `explode block_interaction=tnt` *(control)* | 4 | 261 | **257** |

The control is the point: the census can see destruction, and it sees 257 blocks
of it, with `mob_griefing` true throughout. `block_interaction: "none"` is a real
per-explosion property, not a gamerule in disguise.

## 3. …but at the default offset it also barely damages (`c_entity_damage`)

Six immobile, unarmoured, 400-HP targets at 1–8 blocks. `time set midnight`
matters: at noon these zombies burn, and 0.92 damage/second through 2 natural
armour is almost exactly the number the unoffset explosion produces — which is
how the first run of this rig read as a working explosion.

| case | 1b | 2b | 3b | 4b | 6b | 8b |
|---|---|---|---|---|---|---|
| **CONTROL** vanilla primed TNT, on the floor | 46.92 | 37.74 | 29.43 | 22 | 9.75 | 0 |
| **CONTROL** vanilla primed TNT, one block up | 42.89 | 35.63 | 28.12 | 21.11 | 9.3 | 0 |
| `explode none`, default offset | **1** | **1** | **1** | **1** | **1** | 0 |
| `explode none`, `radius: 8`, default offset | **1** | **1** | **1** | **1** | **1** | **1** |
| `explode none`, `attribute_to_user: false` | **1** | **1** | **1** | **1** | **1** | 0 |
| `explode none`, `offset [0,1,0]` | 43.03 | 35.71 | 28.17 | 21.14 | 9.32 | 0 |
| `explode block_interaction=tnt`, default offset | 2 | 2 | 2 | 2 | 2 | 0 |
| `run_function` → `/damage` in a radius | 12 | 6 | 6 | 0 | 0 | 0 |
| **CONTROL** vanilla TNT, targets floating at centre height | 46.94 | 37.75 | 29.44 | 22 | 9.75 | 0 |
| `explode none` `offset [0,1,0]`, targets at centre height | **46.94** | **37.75** | **29.44** | **22** | **9.75** | 0 |

Read the last two rows together: with the occlusion removed on both sides, the
enchantment's explosion damage is **digit-for-digit identical to vanilla TNT**.
Nothing is wrong with the effect. What is wrong is where it is centred.

The `hit_block` position for a downward hit is `y = -60.00000999999975`, i.e.
`floor(y) = -61`, **inside the stone floor block the arrow hit**. Every
line-of-sight ray from a nearby entity to that centre terminates in stone, seen
percentage is 0, and vanilla's damage formula bottoms out at its constant term —
1.0. Raising the radius from 4 to 8 changes the *reach* (the 8-block target now
takes 1.0) and not the amount, which is the signature of an occlusion floor
rather than a scaling bug. `attribute_to_user` is not involved.

### 3b. And it is not even consistent between surfaces (`c2_orientation`)

The same arrow fired horizontally into a 6-block-thick stone wall, targets
standing beside the flight line:

| enchantment | 1b | 2b | 3b |
|---|---|---|---|
| `explode none`, **default offset** | 45.47 | 37.04 | 29.01 |
| `explode none`, `offset [0,1,0]` | 40.4 | 34.08 | 27.11 |
| `run_function` → `/damage` in a radius | 12 | 6 | 6 |

A wall hit stops the arrow on the **air** side of the face, so the default offset
is *not* occluded and the blast is near-full strength — while the identical
arrow hitting the floor two seconds earlier did 1.0. One authored item, two
completely different weapons depending on what the player shot at, with no
diagnostic anywhere. The `/damage` route is the only row that is the same number
on both surfaces.

## 4. The area-effect half works cleanly (`e_cloud`)

`hit_block` → `run_function` → `summon minecraft:area_effect_cloud` at `~ ~ ~`
with `potion_contents`:

- cloud summoned at the impact point `[300.5, -60.00000999999975, 0.5]`;
- `potion_contents` survives the summon verbatim:
  `{custom_effects: [{duration: 1, id: "minecraft:instant_damage"}, {duration: 200, id: "minecraft:glowing"}]}`;
- **both** bystander players — neither of whom fired the arrow — took 20 → 11 HP
  and were glowing afterwards;
- the cloud was still alive 4 s later.

Being *inside a block* does not matter here: an area effect cloud applies to
entities whose bounding boxes intersect its radius, with no line-of-sight term.
That is why this half needs no offset and no orientation handling.

## 5. The axes a real delve will hit

| axis | measured result |
|---|---|
| **second player** | Both bystanders took the full cloud effect (9 HP, glowing). Effects are not owner-scoped. |
| **reload / restart** | The bow and arrows sat in a chest across a full server **stop/start**. After the restart, the chest still held `bow[enchantments={dwspike:ammo:1}]` and `arrow[custom_data={dw_bomb:1b}] ×4`; the bot took them out, fired, and the effect ran with `ammo_matched = 1`. The binding matrix was re-run after the restart and reproduced all five rows. |
| **shot by a mob** | A skeleton given the enchanted bow (component-era `equipment`) shoots arrows whose `weapon` field **is** the enchanted bow. Its arrows hit the player rather than a block, so `hit_block` did not fire on those; an arrow with the skeleton's own UUID as `Owner` landing on a block **did** fire. The mechanism does not care who shot it. |
| **shot by a dispenser** | Fires nothing, with either ordinary or enchanted ammunition. No weapon item exists to carry the enchantment. |
| **lands in water** | Fires. A 3-deep water column slows the arrow; it settles on the bottom and the effect runs at `[400.5, -63.00000999999975, 0.5]`. |
| **lands on a slab** | Fires, at `[404.5, -59.5, 0.5]` — the slab's top face, correctly, not the block grid. |
| **hits a monster instead of a block** | `hit_block` does **not** fire — measured, target lost only the arrow's 4 HP. Adding `minecraft:post_attack` covers it, but **only when the arrow has an owner**: the same summoned arrow with no owner did nothing, and with a player `Owner` the blast went off at the victim and dealt 46.94 / 37.75 / 29.44 to bystanders at 1/2/3 blocks. The struck entity itself takes no blast damage, only the arrow's. |
| **can it damage the map** | Yes — as **entities**, never as blocks. With `block_interaction: "none"` and 0 blocks destroyed, the same blast still **destroyed an armour stand and an item frame**. A dropped item entity, an `item_display` and a `text_display` all survived. Any box-garden set dressing built from armour stands or item frames is inside the blast's reach. |

## 6. Sketch of the DSL surface this would deserve

Only if the owner wants it; this is a sketch, not a proposal, and it is
deliberately about a **mechanism**, not about a bomb arrow.

The capability is *"a projectile launcher can be given an impact response, and
the response may depend on which ammunition was loaded"*. That belongs to the
**launcher item**, because that is the object class vanilla binds it to — the
same discipline as `sealed_hint` belonging to the clickable, not to the verb.
Concretely the shape that survives the generality test:

- **Where**: on the class/gear item that is a launcher — a first-class
  `on_impact` on the item, not a new stage-5 section and not a `bomb_arrow`
  keyword. A creator building a fire-fighting game gives their hose a water
  burst; a creator building a survey game makes their marker gun drop a beacon.
- **What**: the response is `effects[]` — the **existing** effect vocabulary
  `EnvTrigger` already uses (prose, sound, particles, an area effect, a command,
  a trap). `hit_block` → `run_function` reaches every one of them, so no new
  effect root is needed. This is the whole reason not to invent a bespoke
  "explosion" verb.
- **Which ammunition**: an optional `when_ammo: <item-tag>` matched against the
  arrow's `custom_data`, which the compiler stamps onto the ammunition item it
  emits. The scavenged item stays the arrow.
- **Area damage** is authored as radius + damage, emitted as `/damage` in a
  radius from the impact function — **never** as vanilla `explode` damage, for
  §3. If a campaign wants the vanilla blast's knockback and particles, those are
  separate authored effects.
- **A diagnostic is owed on day one**: any authored `explode`-style effect
  without an offset that lifts it clear of the impacted block is the §3 trap and
  should be a hard error, not a footnote. The general form of this finding is
  "an effect whose damage silently collapses to a constant" — the same class as
  a green gate that binds to nothing.

Open design question for the owner, not for an agent: whether a delve is willing
to accept that the bomb-arrow only works from an engine-issued bow.

## 7. What was NOT measured

- Crossbows, tridents, and the 1.21.11 **spears** (`minecraft:wooden_spear` …
  `minecraft:netherite_spear`). A spear is thrown, so the enchanted item *is* the
  projectile — which would make a self-contained throwable loot item, exactly
  what the arrow could not be. Worth a follow-up if the owner wants the loot to
  be one object.
- `minecraft:apply_mob_effect` and `minecraft:summon_entity` as `hit_block`
  payloads (only `explode` and `run_function` were exercised).
- Blast interaction with `immune_blocks`, `create_fire: true`, and item frames
  containing quest items.
- Any performance question: one blast per shot was never stressed.
- Whether `post_attack` can be made to damage the struck entity as well as its
  neighbours.

## 8. Incidental findings, both of which cost this spike a run

- **Enchantments are a DYNAMIC registry.** `/reload` does **not** pick up a new
  or changed enchantment definition on 1.21.11 — it loads with the world, so the
  pack must be in place before the server starts and any change needs a restart.
  Worse, a bad `supported_items` entry does not warn: it **aborts server
  startup** with `Failed to get element <id>` / `Failed to load registries due to
  errors`. (`minecraft:spear` is not an item id; the spears are per-tier,
  `minecraft:iron_spear` and friends.)
- **`HandItems` is silently ignored on `/summon`** — the rig armed a skeleton
  with a legacy `HandItems:[…]` and got a skeleton holding nothing, which read
  for two runs as "a mob-shot arrow does not fire the enchantment". The engine
  already knows this (`crates/compiler/src/emit.rs::default_equipment`, M2
  round-2 fix 1) and emits component-era `equipment`; the spike rig did not.
  Recorded here because the next rig will reach for the same old spelling.
- A `/setblock` that would place the block already there answers `Could not set
  the block` and a `/fill` with nothing to change answers `No blocks were
  filled` — both are in the rejection regex this repo's spikes share, and both
  are legitimate answers. `fill()` / `killq()` in `measure.mjs` separate "nothing
  to do" from "rejected"; `ok()` still aborts on everything else.
