## What Delvewright is

An automated production line, driven by Claude Code, that outputs **one self-contained
Minecraft adventure "delve" per month** for a fixed group of 1–4 players (the owner and
their friends). Each delve is:

- A story-driven, box-garden (箱庭) level-based adventure map, **2–3 hours** of curated
  play (10h absolute ceiling)
- **Adventure mode**, class selection at start with pre-provided gear, zero grind — no
  mining/leveling loops, no resource farming, no base building
- **Vanilla-first**: gameplay runs on datapacks + command functions + vanilla mechanics
  only. Mods are permitted exclusively in the *tooling/validation* layer (never required
  on the player-facing server)
- Packaged as a **versioned OCI image**: pinned vanilla server + world + config +
  datapack. One `docker run` = a joinable dungeon
- **Validated before human QA**: it must be provably completable by machine before the
  owner spends their one QA hour on it

Long-term (v2, not designed in detail, but not to be precluded): a vanilla survival
hub world connected to delve instances via the vanilla `/transfer` command (1.20.5+),
instances runnable on a remote host.

## Decided architecture

1. **Campaign DSL → deterministic compiler → datapack.** The LLM writes campaigns in a
   structured, schema-enforced DSL (JSON). A deterministic compiler turns DSL into a
   loadable datapack (advancements + scoreboards + mcfunctions + structures). The LLM
   never emits raw mcfunction directly.
2. **Staged, dependency-driven DSL** modeled on the "From World-Gen to Quest-Line"
   pattern (arXiv 2604.25482): world/setting → NPCs → classes/gear → campaign-level
   quest planning → quest expansion. Each stage is a schema; later stages condition on
   earlier stages' outputs.
3. **Maps from a prefab library, not block-by-block generation.** Prefabs stored as
   `.nbt` structures, assembled via vanilla jigsaw / `template_pool` mechanics, with
   compiler-controlled seeds for reproducibility. GDPC/offline assembly is a fallback
   if jigsaw's layout control proves insufficient (revisit-trigger, not built now).
4. **Two-layer validation:**
   - Static: compile-time quest-graph reachability analysis (every quest completable,
     no deadlocks) + command/syntax validation of all compiler output
   - Dynamic: PackTest (GameTest-based, `-Dpacktest.auto` in CI, exit code = failed
     tests) for mechanism/milestone assertions, plus a mineflayer bot harness that
     walks the critical path on a headless server (Carpet fake players for multi-player
     scenarios)
5. **Determinism is a hard invariant**: same DSL + same seed → byte-identical datapack
   and world. Enforced by tests from day one.
6. **Target MC version: pin one 1.20.5+ version as a long-term constant** (needed for
   `/transfer` and modern datapack features).

## Reusable components (evaluated)

- Compiler foundations: beet + mecha (Python, MIT) — OR a Rust-native compiler
  emitting datapack JSON/mcfunction directly. This is Decision Point #1 for the owner.
- Map assembly: vanilla jigsaw/template_pool (primary); GDPC 8.x (MIT) as fallback
- Validation: PackTest (misode), mineflayer (MIT), Carpet mod fake players
- Reference implementations to study, not depend on: Word2Minecraft (story→level
  prompting), Jandhi's Tome (Rust, deterministic RNG + Voronoi/A* assembly)
- License caution: pipeline code will be **GPL**; prefab/content assets must be
  original, CC0, or CC BY. **Never ingest CC BY-NC material.**

## Repository & licensing structure

Monorepo `delvewright`:

```
delvewright/
  CLAUDE.md            # agent constitution: architecture, conventions, forbidden zones
  docs/adr/            # architecture decision records
  docs/specs/          # owner-approved specs, one per feature
  crates/              # Rust workspace: dsl / compiler / orchestrator
  prefabs/             # .nbt library + metadata (git-lfs)
  harness/             # mineflayer bot tests (TypeScript)
  packtest/            # PackTest templates
  validation/          # docker compose: headless server + bot, same image as CI & prod
```

Generated campaigns/worlds do NOT live in this repo — they ship via GitHub Releases /
OCI registry (separate content licensing, likely CC BY-SA; code is GPL).

## Development methodology

- **Spec-driven**: the owner writes/approves specs with machine-verifiable acceptance
  criteria; implementation sessions work against specs. No spec, no feature.
- **CI is the sole arbiter.** The owner does not review line-by-line, but reviews PR
  descriptions and architecture-level diffs. Nothing merges red. Tiered testing:
  unit + static on every push; PackTest integration on PR; full bot playthrough only on
  release candidates (may run on a self-hosted runner later).
- PR-based flow even solo; GitHub Actions on a public repo.
- Every session's lessons get written back into CLAUDE.md / ADRs — repo docs are the
  agents' only persistent memory.
- Repeated workflows become skills / slash commands (`/new-campaign`, `/validate`,
  `/release`).
- Environments: development on the owner's workstation; `validation/` compose profile
  reproduces CI locally; the owner's Raspberry Pi is prod-only (never a dev/test box).
