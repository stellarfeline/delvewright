# i18n — a campaign's l10n sidecars

Live reference for how a delve gets its non-English strings. Another language is
**transcreated** from the English, never translated line by line (CLAUDE.md,
Conventions): each line is rewritten from its intent — what kind of text it is,
who says it, the situation it is said in — with every fact, name and key taken
from the English. How each kind of text and the Chinese should read is
[game-writing.md](game-writing.md). Companion to the
compiler reference's [l10n sidecars](compiler.md#l10n-sidecars-l10ncodejson)
section, which owns the key scheme and coverage rules.

**Generation-time only.** A shipped delve never calls an LLM (CLAUDE.md forbidden
zones): translation happens while the campaign is authored, and the result is
written into the campaign source as `l10n/<code>.json`. The running server talks
to nothing.

**Delivery — the client picks the language (spec-0029).** `delvec build`
ships **every** declared language in one delve: each authored string is emitted as
`{"translate": "delve.<campaign_id>.<l10n key>", "fallback": "<English>"}`, and
every sidecar becomes an `assets/delvewright/lang/<mc_code>.json` inside the
delve's resource pack. A client auto-selects the file matching its own locale;
anything unsupported — an undeclared locale, a key a translator missed, or a
player who **declined** the resource-pack prompt — falls back to the English on
the component itself. A sidecar is shipped, and it is chosen at runtime.

**Your sidecar's keys are the campaign's own; the delve ships them namespaced.**
You write `world.title` in `l10n/zh-cn.json`, and the build emits
`delve.<campaign_id>.world.title`. The two differ because a client merges every
applied resource pack into **one** language table, and a component's `fallback` is
read only when nothing in that table defines its key — so a pack left enabled from
another delve would otherwise answer `world.title` for the delve you are actually
playing. Packs stay enabled: with `DELVEWRIGHT_RESOURCEPACKS_DIR` set to your
instance's `resourcepacks/` directory, `tools/creator/playtest-server.sh`
installs each delve's pack there as `<campaign_id>.zip`, and nothing turns it off
when you leave the server. The prefix is the compiler's, applied on the way out; it
never appears in a sidecar, in `delvec l10n-inventory`, or in anything you write.

`delvec build --lang <code>` is the single-language bake, for local dev and
one-language artifacts. It swaps the strings before
emission, so it carries no translate keys and ships no lang files. The release
path does not use it.

**A translator is never asked for the compiler's own strings.** `New objective: `,
`Delve Complete`, `Choose your class`, the default a bonfire shows when a campaign
authors no label — every entry of `dsl::chrome::ALL` — are **chrome**: compiler-owned keys under
`delvewright.ui.…`, shipped translated with the engine, absent from every
inventory and every sidecar (a sidecar that defines one is `DW0186`). They cost a
campaign nothing and appear in no `l10n-inventory` output. See
[compiler.md § Compiler chrome](compiler.md#compiler-chrome--the-strings-the-compiler-writes-itself).
A language the engine has no chrome table for reads English chrome around its own
translated story — the honest fallback, not a hole in the sidecar.

Two obligations this puts on a translator, both already enforced:

- The **width gates** (`DW0330` on-screen narrate, `DW0331` dialogue option
  labels) check the source and every declared translation. Any declared language
  may be what a player actually sees, so an over-wide translation is a defect in
  the shipped delve.
- The **language code** must resolve to a file the pinned client really loads:
  `dsl::mclang::mc_lang_code` normalises `zh-cn` → `zh_cn` and then checks it
  against `dsl::mclang::CLIENT_LANGS`, the stems derived from Mojang's own
  1.21.11 asset index (`tools/maintenance/derive-client-langs.py`). An unresolved or ambiguous code is
  `DW0184` at validate time, never a language quietly missing from the pack.

- **Entity display names are shared by text.** An actor puppet named exactly like
  the NPC it portrays is inventoried under that NPC's key, and two puppets sharing
  a name share one key — so a character is translated once and cannot be called two
  things in two scenes. A translator simply sees fewer, non-duplicated rows.
  **Wave-mob names are deliberately not pooled**: live
  campaigns keep the keys they already translate, so three waves named
  `Drowned of Poseidon` are three rows a translator can answer three ways. The
  glossary of already-translated proper nouns is what holds them together; the
  prevention lives at authoring time, in the `/new-delve` skill's naming rule
  (*Writing craft* §D), not in the key scheme.

- **A health bar's title is the fight's name, under the name's key.** A
  `health_bar` that states no `title` draws its fight's own name — an actor's
  `name`, or the `name` of a wave's one mob entry — and emits that name's own key
  (`actor.<a>.name`, or whichever key the name is shared under; `wave.<w>.mob.<i>.name`),
  so the character is translated once and the bar cannot call it something else.
  A stated `title` is a row of its own: `wave.<w>.health_bar.title` or
  `actor.<a>.health_bar.title` (spec-0073).

- **Every row records what it was translated from.** A sidecar's `source` map
  holds the canonical English each `content` row was made from, so a rewritten
  authored line is caught (`DW0187`) instead of shipping a translation that is
  present, applied and wrong. Coverage checks compare key *sets* and cannot see
  it: editing a line moves no key. Rows with no `source` are counted and reported
  (`DW0188`) rather than passed over. `tools/creator/i18n-translate.py` writes `source`
  for every row it emits, so re-running it over a sidecar with unguarded rows
  adds `source` without retranslating anything.

## Who writes the other language, and which tool they run

Claude writes the English and, through the campaign documents, each line's
intent. The other language is written by whichever producer is configured, and
**the producer decides the tool**:

| producer | when | tool |
|---|---|---|
| an external OpenAI-compatible LLM API — **DeepSeek recommended** | when `[i18n]` is configured **and** the key env var is set | `tools/creator/i18n-translate.py` |
| the `/new-delve` agent, in-agent | fallback — no config, no key, no network | `delvec l10n-apply` |

**Use DeepSeek for Chinese.** In a blind trial one native Chinese rater
preferred DeepSeek (`deepseek-v4-pro`) transcreating from each line's English,
speaker and situation in 9 of 12 decisive pairs, over the original Chinese (2)
and Claude's rule-guided Chinese (1); measurement in
[game-writing-evidence.md §7](game-writing-evidence.md#7-who-writes-the-chinese--blind-trial).
In-agent Chinese still works and is still validated; it measured worse.

**Neither tool asks a translator for a key.** `i18n-translate.py` calls the model
itself and writes the sidecar; `l10n-apply` takes the translation an agent has
already made and writes the sidecar from it. What they have in common is that the
inventory keys belong to the compiler and to nobody else — which matters because
the effect keys are POSITIONAL (`fx.<quest>.oc.<objective>.<i>`), so inserting one
effect renumbers every sibling and a hand-written merge re-attaches translations
one line over: present, applied, wrong, and no key missing for coverage to catch.

### `delvec l10n-apply` — you translated it, the tool does the keys

```
delvec --lang <code> l10n-apply <campaign-dir> --table <file>
```

The table is a JSON object mapping **canonical English** to its translation —
exactly what `delvec l10n-inventory` showed you, in the `en` column, with nothing
positional in it. `-` reads it from stdin.

What lands is exactly the inventory:

- a row whose English the table carries is written from the table, with its
  `source` recorded, so a later edit of that English is `DW0187` rather than an
  audit;
- a row already translated **from unchanged English** is kept, provenance and
  all, so re-running translates only what moved;
- a row translated with no `source` at all is kept and counted apart: nothing can
  say whether it still matches its English, and discarding a translation over
  that would be worse than saying so.

The run ends by stating `N of M rows translated`, every English string still
untranslated with its key, every table entry that matched no row, and every
English string **two keys share** — the one thing the table form cannot say, so
the sidecar stays directly editable where two identical lines want two different
translations. Exit 1 when anything is missing or unmatched (the signal
`fmt --check` gives); the file is written either way, in canonical form, so
`delvec fmt --check` has nothing to add and two runs over one table write the
same bytes.

The sidecar committed to the campaign repo is the **artifact of record regardless
of who produced it**. Nothing downstream — compiler, validation, release — can
tell, or cares. A hand-edit after the fact is just as legitimate as a generated
line.

## Config

`delvewright.toml` at the engine repo root is the committed, inert convention
file; put real settings in `delvewright.local.toml` (gitignored, same shape,
overrides key by key). Neither is a build input — the compiler never reads them,
so nothing here can move a delve's bytes (ADR-0006).

```toml
[i18n]
provider = "openai-compatible"                # only supported value
base_url = "https://api.deepseek.com/v1"
model = "deepseek-v4-pro"
api_key_env = "DELVEWRIGHT_I18N_API_KEY"      # the NAME of an env var, never a key
temperature = 0.2                             # optional (default 0.2)
batch_size = 40                               # optional keys per request (default 40)
timeout_seconds = 120                         # optional (default 120)
max_retries = 3                               # optional (default 3)
reflect = false                               # optional three-step pass (default false)
```

**The key never enters a file.** `api_key_env` names an environment variable; the
tool reads it at call time, sends it in one `Authorization` header, and never
stores, prints or logs it (an inline `api_key =` is rejected outright). A failing
request reports the endpoint, the step, the status **and the provider's own
explanation**, with the key redacted out of it should a provider ever echo one
back: a bare `HTTP 400` says a request was refused and nothing about why, and the
sentence naming the cause sits unread in the response body. Keep the key in your
shell profile or a secret manager, not in the repo.

**A model id is a measurement, not a memory.** Every id in this file was read
back from the endpoint's own `/models` at the time it was written, and providers
retire ids without notice — a config naming one that no longer exists dies
`HTTP 400` before a single string is sent. `curl -H "Authorization: Bearer $KEY"
<base_url>/models` is the one-line check, and it is worth running before a long
run rather than after it.

### Fallback rule

No `delvewright.toml`/`delvewright.local.toml`, no `[i18n]` section, or the named
env var unset ⇒ **fall back to in-agent translation** (the skill's default
behavior). A *malformed* `[i18n]` — unknown provider, missing `base_url`/`model`/
`api_key_env` — is an error, not a fallback: a typo must not silently downgrade
the pipeline.

### The provider

DeepSeek is the recommended provider for Chinese, at the model the trial
measured. Any OpenAI chat-completions endpoint works by changing `base_url` and
`model`; ask the endpoint what it offers rather than trusting an id — they
rotate, and `/models` answers in one line.

```toml
# DeepSeek — `/models` answered `deepseek-flash`, `deepseek-v4-pro`
base_url = "https://api.deepseek.com/v1"
model = "deepseek-v4-pro"
```

Steps, start to finish:

1. `cp delvewright.toml delvewright.local.toml` and uncomment the `[i18n]` block.
2. Set `base_url` + `model` from the table above; leave
   `api_key_env = "DELVEWRIGHT_I18N_API_KEY"`.
3. `export DELVEWRIGHT_I18N_API_KEY=<the provider's key>` in your shell.
4. Declare the language in the campaign's `world.json`: `"languages": ["zh-cn"]`.
5. `python3 tools/creator/i18n-translate.py <campaign-dir> --lang zh-cn --dry-run` — prints
   the exact prompts and key list, sends nothing. Sanity-check the personas and
   situations.
6. Drop `--dry-run` to run it for real. Read the fact-check report it prints;
   every refused row is named, with the line refused and what failed.

## The tool

```
python3 tools/creator/i18n-translate.py <campaign-dir> --lang <code>
        [--dry-run] [--force] [--batch-size N] [--config PATH]
        [--delvec CMD] [--no-validate] [--reflect | --no-reflect]
```

Stdlib-only python3 (≥3.11). What it does:

1. Runs `delvec l10n-inventory <campaign-dir> --lang <code>` — the authoritative
   key inventory (exactly the key set `DW0180`/`DW0181` enforce). Each row carries
   its canonical English and its **intent**, all derived by `delvec` from the
   campaign documents and none typed by the creator: `kind` (`dialogue`, `bark`,
   `option-label`, `button-tooltip`, `objective`, `refusal`, `prompt`,
   `narration`, `item-name`, `item-tooltip`, `name`, `title`, `description`),
   `speaker` (the NPC, whose persona travels in the request context), and
   `situation` (the quest goal and its `happening`, the objective and what
   completing it does, a cast placement's `doing`, the NPC line an option answers
   and what choosing it does, the nearest effect's `happening`). See
   [compiler.md § the inventory](compiler.md).
2. Sends the pending rows — untranslated, or `stale` (translated from English the
   line no longer reads) — `name`/`title` rows first in batches of their own, so
   every later batch is handed the settled rendering of each name its English
   mentions. The system prompt is a transcreation brief: what each `kind` is for,
   the option-label button budget, the glossary rule, and the target language's
   writing rules **read from [game-writing.md](game-writing.md)** (`## 4.
   Chinese` for `zh-*`, each rule cut before its `**Cited**`/`**Authored**`
   tail), plus the translationese checklist below. A language with a section the
   file no longer has is an error, never a quiet fallback to a translation
   prompt. Low temperature; a reply that drops keys fails the run rather than
   writing a hole. **The reply shape is per step, not per request** — see the
   reflection pass below.
3. **Fact-checks every answer** (below). A failing row is sent back once through
   a `fix` step that names each failure; a row that still fails is **refused**.
4. Writes `l10n/<code>.json` (exactly the inventory — orphans are impossible by
   construction; a refused row is left out, and a stale row this run did not
   redo is dropped rather than kept under today's English) and hands it to
   `delvec fmt`, so what lands on disk is the formatter's own bytes rather than a
   second opinion about canonical form. Then runs `delvec validate` and reports
   coverage. Exits with validate's code, or 1 when any row was refused.

One row as a request carries it (from a `--dry-run` over the gallery):

```json
{
  "key": "dlg.factor.factor-root.opt.0.label",
  "en": "Just looking.",
  "kind": "option-label",
  "speaker": "factor",
  "situation": [
    "Answers the NPC line: \"Counter's open. Everything on it is priced and nothing on it is mine.\"",
    "Choosing it: They leave the counter unbought."
  ]
}
```

### The fact check

Transcreation licenses the model to rewrite, and freer writing loses facts
(game-writing.md §7). The check is the mechanical half of "the facts, names and
keys taken from the English" — what a machine decides without reading for
meaning:

| check | refuses |
|---|---|
| placeholders | a `%s` / `%1$s` / `%%` or `§` formatting code added, lost or changed |
| digits | a number the English writes in digits missing from the line (separators ignored: `10,811` is kept by `10811`) |
| number words (`zh-*`) | `two` … `ninety-nine`, `hundred`, `thousand` with no Chinese numeral or digits for it (`十六`, `四十二`, `一百`, `两`/`俩`); `one` is not read — it is a pronoun more often than a count |
| one name, one rendering | a declared name (every `name`/`title` row) mentioned in the English and not written exactly as the campaign writes it; a mention inside a longer name is held to the longer one |
| one rendering, one name | a `name`/`title` row rendered differently from the rendering the campaign already settled, or rendered the same as a different name |

The name map is the sidecar's own renderings (stale rows and rows being redone
excluded) plus every name this run accepted, first rendering wins. The report
states the rows checked, the names held, the rows accepted (and how many after one
correction), and each refused row with its English, the refused line and every
failure. A refused row is a defect the creator fixes: write the line into the
sidecar by hand (or with `delvec l10n-apply`) and validate.

**Idempotent**: a re-run sends only keys the sidecar lacks or holds stale, and
rewrites the file byte-identically when nothing is pending. `--force` redoes
everything.
`--delvec` (or `$DELVEC`) names the binary; without either, the `delvec` on `PATH` (then the tree's `target/release/delvec`) is used when it answers the engine version `versions.toml` pins, and the tool exits 2 naming what it found when none does. It never builds one.

**Canonical form has one authority, and it is not this tool.** A written sidecar
goes through `delvec fmt`, so `delvec fmt --check` (`DW0773`, error tier) has
nothing left to say about it and there is no follow-up format to remember. That
includes the envelope's `dsl_version`: the formatter stamps the version this
engine implements (ADR-0024), so a sidecar carrying an older claim forward is a
document the check refuses. `crates/delvec/tests/i18n_sidecar.rs` is what binds
it — the real writer writes a real file and the real formatter judges it.

## The reflection pass (`--reflect`)

An optional second opinion on every batch. The blind trial measured the single
pass (game-writing-evidence.md §7); `--reflect` with transcreation is
unmeasured, so the `/new-delve` skill does not pass it. `--reflect` runs each
batch as **three steps** instead of one:

1. **Transcreate** — as above.
2. **Criticise** — a fresh call reads source, intent and draft side by side and
   writes free-text criticism, one suggestion per problem, each naming its key.
   It is forbidden from writing a corrected line: making the model *state the
   defect* is what stops step 3 from being a second roll of the dice.
3. **Revise** — the writer applies the critique, may reject it where it judges
   it wrong, and returns already-good lines **byte-identical**.

**Each step declares the reply shape its own prompt asks for.** Steps 1 and 3 ask
for one JSON object and send `response_format: {"type": "json_object"}`; step 2
asks for prose and sends no `response_format` at all. That is not a nicety: a
provider enforces the agreement. OpenAI and DeepSeek both refuse `json_object`
with `HTTP 400 "Prompt must contain the word 'json' in some form"` when the
prompt never asks for JSON, and the critique prompt deliberately never does. A
step that asks for `json_object` while its own prompt never says `json` is
refused locally, before the request is spent.

The critique axes:

| axis | what it catches |
|---|---|
| accuracy | additions, mistranslations, omissions, untranslated leftovers, mangled placeholders |
| fluency | target-language grammar and idiom, needless repetition, anything a native reader must re-read — **plus the target language's translationese checklist** |
| style / register | the speaking NPC's `speech_style`, hand-made-adventure register, strings that still fit a chat line, and the **option-label button budget** below |
| terminology | glossary proper nouns verbatim, one English term rendered one way everywhere |

**Option labels carry a width budget.** A
`.opt.<n>.label` is drawn on a fixed-width dialog button — vanilla's default 150
GUI px, since the compiler sets no `width` — and a label too wide for it
*scrolls* instead of wrapping. Roughly 146 font px are usable: about **20 Latin
or 12 Han characters**. Chinese is the risk case, because a faithful translation
of an English label that already sits near the limit will overrun it. Both the
translate and the critique prompts state the budget, and a translated label
*shorter* than its English source is correct here. The `/new-delve` skill carries
the same rule for the English source (*Writing craft* §C), and the compiler
already rejects an over-wide label outright — `DW0331`, error tier, measured over
the English source **and** every declared-language sidecar.

**Translationese is language-specific and lives in the prompt.** For `zh-*` the
tool carries a 翻译腔 checklist — 名词化, 弱动词 (进行/加以/作出), 的的不休,
over-marked 被, front-loaded relative clauses, reflexive 地/们/当……的时候,
redundant possessives — under one governing rule: exhaust the constructions
Chinese already has before importing one. 信达雅 is framed as a precedence
(信 → 达 → 雅, with 雅 meaning *the register the scene calls for*, not ornament).
A language with no checklist simply gets the general axes; a wrong checklist
would be worse than none.

**Anti-churn is explicit.** Reflection prompts rewrite unconditionally unless
told not to, and an unconditional rewrite degrades text that was already right —
so "no change" is stated as an expected verdict in step 2 and byte-identical
return is mandated in step 3.

Cost: three requests per batch instead of one. Off by default; `--reflect` turns
it on for a run, `[i18n] reflect = true` for a repo, `--no-reflect` overrides the
config back off. Every prompt in all three steps is printed by `--dry-run`. The
fact check runs on the revision, exactly as on a single pass.

Provenance: the three-step shape and the four critique axes follow
[`andrewyng/translation-agent`](https://github.com/andrewyng/translation-agent)
(MIT); the translationese checklist and the 信达雅 framing are our own, re-derived
rather than copied — see `docs/ACKNOWLEDGEMENTS.md`.

Art-styled `narrate` strings are glyph-validated against the `delve:art` font
(`DW0328`) in every declared language — if a translated art title trips it, that's
a real defect in the translation, not a check to relax.

## Comparison workflow

The point of the pluggable provider is to compare translators on the same
campaign:

1. Translate with the API (`--force` to redo an in-agent sidecar).
2. `git diff` the sidecar — the English side is fixed, so the diff *is* the
   comparison.
3. Owner reviews in-game where it matters: `delvec build --lang <code>` and play.
4. Hand-edit anything that reads wrong; re-running the tool preserves every line
   already present (only `--force` overwrites), so review edits survive.

Swapping provider = editing `base_url`/`model` and re-running with `--force`.
