## Diagnostics

### DW046x — the NPC scene ledger (`compiler::cast`; spec-0020)

This module's rows of a section whose prose is on the [`delvec::compiler::cast` page](cast.md#dw046x--the-npc-scene-ledger-compilercast-spec-0020).

| Code | Meaning |
|------|---------|
| `DW0886` | **This pool cannot stand on this horizon.** `compiler::seating::check`, bound in the one validation funnel every subcommand goes through (`main::validate_loaded`), **validation tier, exit 1** — on `DW0855`'s own precedent, and for its reason: the whole verdict is a fact about the documents and the library (the declared base, the pools the world names, the members those pools hold, each member's metadata and its bytes), so nothing has to be placed to know it and a creator should not spend a build to learn that the pieces they chose cannot stand where they put them. The `DwCode` declares build tier, which is what happens if the same rule refuses with a build under way: `plan::area_base_y` derives an ocean area's origin from the same number and cannot proceed without it. **One question, several answers, so one code.** *No walk plane*: the piece declares no `walk_y`, on any base, and there is no default to fall back on. *Wading under the sea*: the base is `ocean` and the piece's own bytes stand a body below its declared walk plane, so those cells land at or below y=62. *An unstated shore*: the base is `ocean` and the piece authors water in the sea's own plane while declaring no `waterline_y`, so nothing states where it meets the sea — water ABOVE that plane is a cistern rather than a shore and is not this finding. *Fluid off the world*: the base is `void` and the piece's fluid reaches its own outer face, which is the static form of `DW0318`'s finding. *A side declared shown with no block on it*: a `shown_faces` entry names a side the piece's own bytes put nothing on, or is not a side — `DW0885`'s second arm, a fact about the bytes, on every base. *Outside unanswered*: the set lets a party outside and a member puts blocks on a side neither the horizon buries nor `shown_faces` declares — `DW0885`'s first arm asked before placement by `seating::set_exposure`, with the build's own predicates (`burial::solid_sides`, `burial::ambient_buries`, `nav::Ambient::of_base`). A member lets the party outside when its own air, flooded from its standable cells, reaches its box boundary anywhere but a socket's opening (`PieceFacts::opening_to_outside`; a mated socket opens into a neighbour and an unmated one is sealed by `solver::seal_layout`). A neighbour is never credited, because a draw promises none. The sea is credited only where the member's height is known: every socket in the set joins at one rise above the walk plane (`PieceFacts::socket_rises`), so every member stands on the plane the origin derives from; a set whose rises differ can stand a member anywhere. `valley` is not asked: its ground is terrain around a declared extent, and the only `areas[]` campaign reaching it is one area bound to one prefab, whose outside the build judges against the landform it builds. Judged per area, which is sound across areas because areas stand `plan::AREA_SPACING` (256) blocks apart and the build's party-air flood reaches two cells past a piece; a layout spanning more than 253 blocks is the stated residual, as is an edit that carves a way out after placement. On an ocean campaign with `pool/cave-shore` beside `pool/vertical-keep`, `prefab seating` prints `REFUSED 0 of 13` and `analyze` exits 1 with 13 × `DW0886` — the same geometry `build` refuses with `DW0885` — and with the sides the refusal names declared shown, `analyze` and `build` both exit 0. Over the content library at its pinned revision the shape refuses `pool/cave-shore` on `void` and `ocean` and `pool/island` on `void`, and seats `pool/island` on `ocean` (its four members declare all four sides shown) and both keep pools on every base. The pair is held on one geometry in `crates/delvec/tests/piece_exposure.rs` (`the_seating_answer_is_the_exposure_answer`: sealed, open and silent, open and declared, an empty side declared, a word that is not a side — refused by both or by neither), and in the gallery by `a-face-nothing-stands-in-front-of`. *Two walk planes in one set*: the base derives an origin from a walk plane and the members of the area's piece set do not agree about theirs — a property of the SET, which no member can answer, because every one of them may be individually perfect and the solver's draw decides which stands at the derived origin. A check asking every question about each member and none about the set would call `pool/island` (`walk_y` values `[2, 3]`) and `pool/cave-shore` (`[1, 2]`) seatable while the build's origin derivation refuses both. `compiler::seating::set_walk_plane` is the one implementation, and its three callers are the command, this validation check and the origin derivation. **It opens the `.nbt`**: a verdict computed from declarations alone reports a library of waterline fictions as seatable. **`DW0855` is not restated here** — one rule, one code; this message names its case so that a creator reading either one reads a single answer about which base seats what. **The walk plane binds on every base.** The missing-`walk_y` shape is computed on every base and refused on every base, from the one rule in `seating::seating_reasons` that `delvec prefab seating` reads — so the command's verdict about a library and the campaign's verdict about the pieces it seats are one verdict, not two. The ocean is where the number is also CONSUMED, because `plan::area_base_y` derives the area origin from it; `void` and `valley` state their own datum for the origin and still owe the declaration, because a piece with no walk plane is a piece nothing can say a body stands on (spec-0060 §4 rule 1: a piece placed on ANY base without it is this code). Measured over the pinned content library: 38 of 38 piece documents declare `walk_y`, and the command reports this shape on no member of any of the four pools' 42 memberships on `void`, `ocean` or `valley`; over the gallery library, on none of the six. The refusal is proven on two bases in the gallery — `a-piece-with-no-walk-plane` (`ocean`) and `a-walk-plane-the-void-still-owes` (`void`) — and the move each one names is reachable on both (`crates/delvec/tests/remedy_reachability.rs`). **It reaches BOTH placement models.** A campaign places its pieces with `areas[]` or with a site plan and never both (`DW0839`), so a rule that read one model had nothing to say about half the campaigns this engine accepts — and about EVERY campaign on the base that builds terrain, since `valley` rings a declared extent and a plan was then the only statement of one (`DW0855`; a one-area campaign's single prefab is the other). Without this arm, the gallery's site-plan overlay with nothing changed but `horizon: ocean` would analyze green while `node/undercroft` stands two courses under the sea plane, and the build would refuse it at `DW0344` after paying for the assembly, with moves naming a `blockout/node/undercroft.json` no author can edit. `check` reads the plan's own resolver (`siteplan::placed_boxes`, never a second reading of the document, because a box's corner is derived from the packing) and asks each placed box the same question, through the same predicate `seating::feet_under_the_sea(base, world_y)` the piece arm goes through: **at the world y this thing puts a party's feet, does the base put sea there?** A prefab reaches that number by derivation; a box states it, because `PlacedBox::floor` IS a walk plane in world coordinates. **Exactly one of the five shapes crosses**, and the module states per shape why the others cannot: *no walk plane* is answered by the schema (`floor` is required, and a box naming an undeclared datum is `DW0112` before this); *an unstated shore* and *fluid off the world* need authored bytes, and `blockout::palette` is a fixed set of opaque cubes with no water in it; *two walk planes in one set* is a property of a POOL the solver draws from, and a plan states every box's plane individually. The moves are the plan's own — RAISE the place's `floor`, which a named `datum` does for every place standing on it at once, or CHOOSE a base with no sea — and there is deliberately no move naming a `walk_y`, because a site plan's mass is derived and authored by no one, so there is no prefab document to put one in. Both are taken green in `crates/delvec/tests/remedy_reachability.rs`; the refusal is proven in the gallery by `a-place-cut-below-the-sea`. **Binding**: `seating binding: horizon base …` states each placement model with its own numerator and denominator — `areas[]:` areas examined of areas, members, how many of them open outward, `.nbt` opened, and waterline declarations examined against declarations borne out; `site plan:` boxes judged of boxes the plan states — on every run, including the one that finds nothing, so the model a campaign did not use reads as a zero rather than as a silence. |
| `DW0887` | **A declared waterline that is not in the piece's bytes.** `compiler::seating::waterline_reason`, validation tier (exit 1) when a campaign names the piece, and swept over a whole library by `delvec prefab audit <library dir>` from the same implementation. A `waterline_y` is a claim about the bytes — the local y of the piece's top authored `minecraft:water` block — and the check that consumes the field asks only whether `pos.y + waterline_y` equals sea level, never whether there is water at that plane; this code reads the bytes. **Two shapes**: declared with no water anywhere in the piece, and declared over water standing at another plane. **Base-independent by construction**: the fiction is in the library, not in the campaign, so the same document is refused whatever base the world declares. Measured on the shipped content library at the pinned revision: 4 declarations, 4 borne out, 0 refused. That is a green over a library whose fictions were repaired, which is not a green over nothing but is not a proof either, so the property is bound by a PLANTED one — `crates/delvec/tests/seating_cli.rs` writes a `waterline_y` onto a piece that authors no water and checks the sweep refuses it, which holds *a declaration-only implementation reports N of N* against any library at all. **Three doors, one rule.** Validation when a campaign names the piece; `delvec prefab audit <library dir>` over a whole library; and `delvec prefab audit <asset>` at the **admission event**, over one template or one tile-set manifest measured as one assembled building. That last is the door that matters: nothing in any gate hands this command a directory — the admission procedure and the content repository's palette job both walk the pieces one file at a time. Every per-file report carries a `waterline` binding whose `state` is `checked`, `undeclared`, `no-document` (an ingested piece audited before its metadata exists) or `unreadable` (a document nobody can parse is not a document with no waterline) — four facts one silence would conflate. **No generator holds a private copy of this rule** (`prefabs/gallery-generator`'s `assert_the_shore_is_standable` checks only that anchors stand clear of its tide pool): the gallery's shores are proven the way every creator's are. **Prescription**: delete the declaration (a piece that authors no shore has no waterline to state, and deleting it does not make the piece unseatable on an ocean, which seats it by `walk_y`), correct the number to the local y the bytes hold, or author the shore the piece claims. Never answer it by changing the horizon. **Binding**: `waterline audit binding:` states documents read, `.nbt` opened, declarations examined, borne out and refused. |
